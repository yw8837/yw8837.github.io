01 · JOIN이란 — 두 테이블을 가로로 잇기#

JOIN은 두 개 이상의 테이블을 연결·결합해 하나의 결과로 출력하는 것이다. 어제 배운 집합 연산자가 행을 세로로 쌓았다면, JOIN은 컬럼을 가로로 늘려 붙인다고 생각하면 직관적이다.

먼저 연산자 기준으로 두 갈래다.

분류사용 연산자의미
EQUI JOIN (등가)=두 테이블에서 정확히 일치하는 행을 결합. 대부분 기본키-외래키 관계 기반
Non-EQUI JOIN (비등가)>, >=, <, <=, BETWEEN정확히 일치하지 않는 범위 조건으로 결합

💡 팁: 강사님은 실무에서 등가 조인(EQUI)이 대부분이고 비등가 조인은 쓰는 일이 드물다고 했다. 일단 “JOIN = =로 두 테이블 잇기"부터 몸에 익히면 된다.

02 · INNER JOIN — 양쪽에 다 있는 행만 (교집합)#

INNER JOIN(내부 조인)은 조인 조건을 만족하는, 즉 양쪽 테이블에 짝이 있는 행만 반환한다(교집합). INNER는 기본값이라 생략하고 JOIN만 써도 똑같다.

조인 조건을 거는 방법이 세 가지인데, 차이를 표로 정리하면 이렇다.

방식쓰는 법특징
ONON a.컬럼 = b.컬럼가장 일반적. 컬럼명이 서로 달라도 가능
USINGUSING(공통컬럼)두 테이블의 같은 이름 컬럼에만. 컬럼·테이블 별칭 금지 (SQL Server 미지원)
NATURALNATURAL JOIN같은 이름 컬럼 전체 자동 조인. 추가 조건·별칭 금지
-- INNER JOIN 기본형 (ON)
SELECT * FROM 테이블1 [INNER] JOIN 테이블2
ON 테이블1.컬럼명 = 테이블2.컬럼명;

-- 같은 이름 컬럼만 골라 조인
SELECT * FROM 테이블1 JOIN 테이블2 USING(기준컬럼);

-- 같은 이름 컬럼 전체 자동 조인
SELECT * FROM 테이블1 NATURAL JOIN 테이블2;

💡 팁: 강사님은 ON만 확실히 익히면 충분하다고 했다. USING·NATURAL은 제약(별칭 금지 등)이 많고 환경에 따라 동작이 달라 실무에서 잘 안 쓴다. “있다는 것만 알고 ON으로 다 처리한다"고 생각해도 된다.

(참고: 슬라이드 INNER JOIN 예시에 ON a.CALSS = b.ID가 있는데, CLASS의 오타로 보인다. 개념 이해엔 지장 없다.)

03 · CROSS JOIN — 모든 조합 (카티션 곱)#

CROSS JOIN은 조인 조건이 아예 없을 때 생기는 모든 행의 조합이다. 결과 행 수 = 테이블A 행 수 × 테이블B 행 수. 그래서 카티션 곱(Cartesian product)이라 부른다.

SELECT * FROM PERSON
CROSS JOIN PUBLIC_TRANSPORT;   -- 사람 × 교통수단 = 모든 조합

💡 팁: 결과 행이 곱셈으로 폭증한다(100행 × 100행 = 1만 행). 실무에서 의도적으로 쓸 일은 거의 없고, 오히려 ON 조건을 깜빡해서 실수로 CROSS JOIN이 되는 경우를 조심해야 한다.

04 · OUTER JOIN — 짝 없는 행도 살려두기 (LEFT/RIGHT/FULL)#

OUTER JOIN(외부 조인)은 INNER와 달리, 한쪽에만 있고 짝이 없는 행도 결과에 포함한다. 빈 자리는 NULL로 채운다. “짝 있는 것만"이 INNER, “짝 없어도 살려둔다"가 OUTER다.

종류보존하는 쪽의미
LEFT [OUTER] JOIN왼쪽 테이블 전부왼쪽은 다 남기고, 오른쪽 짝 없으면 NULL
RIGHT [OUTER] JOIN오른쪽 테이블 전부오른쪽은 다 남기고, 왼쪽 짝 없으면 NULL
FULL OUTER JOIN양쪽 전부어느 쪽이든 짝 없어도 다 남기고 NULL
-- LEFT: USER는 전부 남기고, 매칭 안 되는 CLASS는 NULL
SELECT * FROM USER LEFT [OUTER] JOIN CLASS
ON USER.CLASS_ID = CLASS.CLASS_ID;

🚨 여기서 DBMS 차이가 갈린다#

(1) Oracle의 (+) 구문 — Oracle은 표준 LEFT/RIGHT 대신 WHERE절에서 데이터를 보존할 테이블의 반대쪽 에 (+)를 붙이는 독특한 옛 문법이 있다.

-- Oracle 전용: USER를 다 보존 → 반대쪽(CLASS)에 (+)
SELECT * FROM USER, CLASS
WHERE USER.CLASS_ID = CLASS.CLASS_ID (+);

(2) MySQL은 FULL OUTER JOIN 미지원 → UNION으로 대체 — LEFT JOIN과 RIGHT JOIN 결과를 어제 배운 UNION(중복 제거)으로 합치면 FULL OUTER JOIN과 같은 효과가 난다.

SELECT * FROM CLASS LEFT OUTER JOIN USER ON USER.CLASS_ID = CLASS.CLASS_ID
UNION
SELECT * FROM CLASS RIGHT OUTER JOIN USER ON USER.CLASS_ID = CLASS.CLASS_ID;

⭐ ON vs WHERE — OUTER JOIN의 핵심 함정#

OUTER JOIN에서 조건을 ON에 거느냐 WHERE에 거느냐는 결과가 완전히 다르다.

위치역할OUTER JOIN에서
ON조인 조건짝 없는 행도 NULL로 보존
WHERE조인 후 필터NULL 행까지 걸러냄

그래서 “짝이 없는 행"을 찾는 단골 패턴이 바로 이것이다.

-- 앨범이 하나도 없는 아티스트 찾기 (chinook)
SELECT ar.Name AS ArtistName
FROM artists ar
LEFT JOIN albums al ON ar.ArtistId = al.ArtistId
WHERE al.AlbumId IS NULL;     -- 오른쪽 짝이 없는(NULL인) 행만 = 앨범 없는 아티스트

💡 팁: 강사님 권장 학습 우선순위는 INNER · LEFT · RIGHT + SELF다. Oracle (+)·NATURAL·USING·CROSS는 “이런 게 있다"는 개념만 알면 된다. LEFT JOIN ... WHERE 오른쪽키 IS NULL은 “없는 것 찾기"의 정석이니 꼭 외워두자.

05 · SELF JOIN — 같은 테이블을 자기 자신과 잇기#

SELF JOIN은 하나의 테이블을 별칭 2개로 분리해 자기 자신과 조인하는 것이다. 테이블도 컬럼도 이름이 같으니, 구분하려면 별칭(alias)이 필수다. 오늘 라이브에서 가장 집중한 주제다.

대표 쓰임은 두 가지다.

  • 계층형(상사-부하): employees처럼 한 직원이 다른 직원(관리자)을 가리키는 자기참조 구조. employees.ReportsTo → 내 관리자의 EmployeeId.
  • 같은 그룹 내 쌍 비교: “같은 국가 고객끼리”, “같은 앨범 안 트랙끼리” 비교.
-- 계층형: 직원 ←→ 그 직원의 관리자 (chinook)
SELECT e.FirstName AS 직원, m.FirstName AS 관리자
FROM employees e
LEFT JOIN employees m ON e.ReportsTo = m.EmployeeId;   -- 같은 테이블 두 번(e, m)

💡 라이브 Q&A — “ReportsTo 같은 자기참조 컬럼이 없는 Track/Customer에서도 SELF JOIN이 되나요?” → 된다. 전형적 SELF JOIN은 ReportsTo 같은 자기참조 FK가 가장 자연스럽지만, 공통 그룹키(같은 AlbumId, 같은 Country)로 같은 테이블 행끼리 묶어 비교하는 것도 SELF JOIN이다. 이때 조인 키는 자기참조 FK가 아니라 “같은 그룹"을 뜻하는 컬럼이 된다.

💡 팁: 쌍 비교에서 c1.CustomerId < c2.CustomerId 같은 부등호 조건을 거는 이유는 (A,B)와 (B,A) 같은 중복 쌍과 자기 자신(A,A)을 제거하기 위해서다. SELF JOIN 쌍 비교의 단골 트릭이다.

06 · 서브쿼리란 — 쿼리 안에 또 쿼리#

서브쿼리(Subquery) 는 SQL 문 안에 들어 있는 또 다른 SELECT 문이다. “평균보다 비싼 제품"처럼 먼저 어떤 값을 구하고, 그 값을 조건으로 써야 할 때 쓴다. 분류 기준이 두 개라 헷갈리는데, 따로 보면 쉽다.

(A) 동작 방식 — 연관 / 비연관#

분류메인쿼리 컬럼 참조?실행 횟수
비연관(Un-correlated)X서브쿼리를 딱 한 번 실행해 값을 제공
연관(Correlated)O메인쿼리 행마다 서브쿼리를 다시 실행
-- 비연관: 전체 평균 단가보다 비싼 트랙 (서브쿼리 한 번만 실행)
SELECT Name, UnitPrice FROM tracks
WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM tracks);

-- 연관: 자기가 속한 '앨범의 평균 재생시간'보다 긴 트랙
SELECT t.Name, t.Milliseconds
FROM tracks t
WHERE t.Milliseconds > (
    SELECT AVG(t2.Milliseconds) FROM tracks t2
    WHERE t2.AlbumId = t.AlbumId    -- 메인쿼리 t.AlbumId를 참조 ← 이게 '연관'
);

💡 팁: 연관 서브쿼리를 알아보는 법 — 서브쿼리 안에 메인쿼리의 별칭(t.AlbumId)이 들어와 있으면 연관이다. “각 행마다 기준이 달라진다”(앨범마다 평균이 다름)면 연관일 가능성이 높다. 라이브에서 강조한 핵심 개념(Day04_2 문제6)이다.

(B) 반환 형태 — 단일행 / 다중행 / 다중컬럼#

서브쿼리가 몇 행, 몇 컬럼을 돌려주느냐에 따라 쓰는 연산자가 다르다.

형태결과사용 연산자
단일행1행 1값=, <, >, <=, >=
다중행여러 행IN, EXISTS, ALL, ANY
다중컬럼여러 컬럼(col1, col2) IN (...)

다중행 연산자 4종의 의미는 이렇다.

연산자의미
IN서브쿼리 결과 중 하나라도 일치
EXISTS결과가 존재하는지 여부만 확인(있냐 없냐)
ALL결과의 모든 값에 대해 조건 만족 (예: >= ALL = 최댓값 이상)
ANY결과 중 하나 이상 만족 (예: >= ANY = 최솟값 이상)
-- IN: 품질팀 또는 영업팀 소속 직원
SELECT NAME FROM EMPLOYEE
WHERE DEPARTMENT_ID IN (SELECT ID FROM DEPARTMENT WHERE NAME='품질' OR NAME='영업');

-- 다중컬럼: 각 부서의 최고 급여 직원
SELECT NAME, SALARY FROM EMPLOYEE
WHERE (DEPARTMENT_ID, SALARY) IN
      (SELECT DEPARTMENT_ID, MAX(SALARY) FROM EMPLOYEE GROUP BY DEPARTMENT_ID);

🚨 SQLite 주의 — ALL / ANY 미지원#

위 표의 ALL/ANY는 표준 SQL 문법(슬라이드) 이다. SQLite는 ALL/ANY를 지원하지 않아 실습(Day04_2)에서는 MAX/MIN으로 바꿔 쓴다.

표준(슬라이드)SQLite 대체(실습)의미
>= ALL (서브쿼리)>= (SELECT MAX(...) ...)모든 값 이상 = 최댓값 이상
>= ANY (서브쿼리)>= (SELECT MIN(...) ...)하나 이상 = 최솟값 이상

💡 팁: 라이브에서 다중컬럼 서브쿼리((AlbumId, Milliseconds) IN (...)로 앨범별 최장 트랙)를 새로 강조했다. HAVING절에도 서브쿼리를 쓸 수 있고(“앨범별 트랙수 > 전체 평균 트랙수”), “판매 안 된 트랙"은 NOT IN (SELECT TrackId FROM invoice_items)로 푼다.

07 · 스칼라 서브쿼리 — 값 하나를 컬럼처럼#

스칼라 서브쿼리(Scalar Subquery) 는 1행 1컬럼(값 하나) 만 돌려주는 서브쿼리다. 값 하나니까 SELECT 절·WHERE·HAVING 어디서든 일반 값처럼 끼워 넣을 수 있다.

-- SELECT 절: 부서명 옆에 그 부서 인원수를 붙이기
SELECT NAME,
       (SELECT COUNT(*) FROM EMPLOYEE E WHERE E.DEPARTMENT_ID = D.ID) AS 인원수
FROM DEPARTMENT D;

🚨 SQLite 주의 — DUAL 없음: Oracle은 “테이블 없이 값만 계산"할 때 FROM DUAL이라는 더미 테이블을 쓴다. SQLite엔 DUAL이 없어 FROM 절을 아예 생략하고 SELECT만 쓴다.

-- Rock 장르 비율 (Oracle은 ... FROM DUAL, SQLite는 FROM 생략) — chinook 실습
SELECT ROUND(
  CAST((SELECT COUNT(*) FROM tracks t JOIN genres g ON t.GenreId=g.GenreId WHERE g.Name='Rock') AS REAL)
  / CAST((SELECT COUNT(*) FROM tracks) AS REAL), 4
) AS RockRatio;     -- FROM 절 없음

08 · VIEW(뷰) — 복잡한 쿼리에 이름 붙여 저장하기#

VIEW(뷰) 는 다른 테이블에서 파생된 가상 테이블이다. 실제 데이터를 따로 저장하는 게 아니라(논리적으로만 존재), 뷰를 조회하면 DBMS가 뷰 정의 쿼리를 대신 실행해 준다. 자주 쓰는 복잡한 조인 쿼리를 한 번 정의해 두고, 다음부턴 SELECT * FROM 뷰이름처럼 간단히 부르는 것이다.

장점설명
독립성원본 테이블 구조가 바뀌어도 뷰를 쓰는 프로그램은 그대로
편리성복잡한 쿼리를 미리 정의 → 이후 짧게 호출
보안성민감 컬럼은 빼고 보여줄 부분만 노출, 원본 테이블 접근 제어

특징도 알아두자.

  • 뷰 위에 또 다른 뷰를 만들 수 있다(뷰의 중첩).
  • 뷰 정의는 수정 불가 → 바꾸려면 삭제 후 다시 만든다.
  • 원본 테이블이 삭제되면 그 위에 만든 뷰도 함께 사라진다.

🚨 SQLite 주의 — CREATE OR REPLACE VIEW 미지원#

표준/Oracle은 CREATE OR REPLACE VIEW로 한 번에 덮어쓰지만, SQLite는 이 구문이 없다. 그래서 DROP VIEW IF EXISTS로 먼저 지우고 다시 만든다.

-- 표준/Oracle
CREATE OR REPLACE VIEW view_name AS SELECT ... ;

-- SQLite (실습) — 지우고 새로 만들기
DROP VIEW IF EXISTS view_name;
CREATE VIEW view_name AS SELECT ... ;

💡 팁: 뷰는 “복잡한 조인 쿼리를 즐겨찾기 해두는 것"으로 이해하면 쉽다. 단, 데이터를 따로 저장하진 않으니 조회할 때마다 원본 쿼리가 다시 도는 점은 기억하자. (강사님: 조인 포함 뷰의 UPDATE 가능 여부 등 갱신 제약은 추후 확인 예정.)

09 · Python + SQLite 연동 — DB를 프로그래밍 언어에서 다루기#

마지막으로, DB를 저장소로만 두고 실제 분석·시각화는 Python에서 하는 흐름을 배웠다. DB에 접속 → 쿼리 실행 → 결과를 받아 가공·그래프. Python 표준 라이브러리 sqlite3만 있으면 된다.

import sqlite3

def run_query(db_path, sql, params=()):
    """SQLite 쿼리 실행 후 (컬럼명, 행들) 반환"""
    conn = sqlite3.connect(db_path)       # 1) DB 파일에 연결
    conn.row_factory = sqlite3.Row        #    컬럼명으로 접근 가능하게
    cur = conn.cursor()
    cur.execute(sql, params)              # 2) 쿼리 실행
    rows = cur.fetchall()                 # 3) 결과 모두 받기
    conn.close()                          # 4) 연결 닫기
    return [d[0] for d in cur.description], rows

💡 팁: 라이브에서 짚은 SQLite vs MySQL 차이 — SQLite는 파일 하나(chinook.db)에 연결하면 끝이지만, MySQL은 호스트·유저·비밀번호·포트로 원격 서버에 접속한다. 그래서 connect()에 넘기는 정보가 다르다. 그리고 작업이 끝나면 conn.close()로 연결을 닫아야 한다 — 안 닫으면 “파일이 잠겼다(database is locked)“는 에러를 만날 수 있다(실습 노트 참고).

SQL로 뽑은 집계 결과는 그대로 matplotlib 막대그래프로 그릴 수 있고(국가별 고객 수, 제품라인별 매출 등), 새 DB를 만들어 CREATE/INSERT/UPDATE/DELETE(CRUD)와 JOIN·서브쿼리까지 Python 안에서 다 돌려봤다. 자세한 실행 결과는 코드 노트에 있다.

10 · 강사님이 강조한 포인트 (정리)#

  • JOIN = 두 테이블을 가로로 잇기. 연산자 기준(EQUI/Non-EQUI) + 형태 기준(INNER/OUTER/SELF…).
  • 학습 우선순위: INNER · LEFT · RIGHT + SELF. NATURAL/USING/CROSS·Oracle (+)는 개념만.
  • OUTER JOIN의 ON vs WHERE: ON은 짝 없는 행 보존, WHERE는 NULL까지 제거. “없는 것 찾기” = LEFT JOIN ... WHERE 오른쪽키 IS NULL.
  • SELF JOIN은 별칭 필수. 자기참조 FK(ReportsTo)뿐 아니라 공통 그룹키로도 가능. 쌍 비교는 <로 중복 제거.
  • 서브쿼리 두 축: 동작 방식(연관/비연관) × 반환 형태(단일행/다중행/스칼라). 연관 = 서브쿼리가 메인쿼리 컬럼 참조 → 행마다 재실행.
  • SQLite 대체 문법 암기: ALL/ANY → MAX/MIN, DUAL → FROM 생략, CREATE OR REPLACE VIEW → DROP 후 CREATE.
  • VIEW = 복잡한 쿼리 즐겨찾기. 논리적 가상 테이블, 정의 변경 불가(삭제 후 재생성).
  • Python sqlite3: connect → cursor.execute → fetchall → close. 안 닫으면 파일 잠김 에러.
  • 다음 수업 예고: 윈도우 함수(프레임/범위 개념 예습 권장).

마무리#

오늘은 여러 테이블을 다루는 두 축을 깊게 팠다. JOIN으로 두 테이블을 가로로 이으면서 INNER(짝 있는 것만)·OUTER(짝 없어도 보존)·SELF(자기 자신과)까지 종류를 갈랐고, 특히 OUTER JOIN의 ON vs WHERE와 SELF JOIN(자기참조든 그룹키든)이 핵심이었다. 서브쿼리는 동작 방식(연관/비연관)과 반환 형태(단일행/다중행/스칼라) 두 기준으로 정리하면 더는 헷갈리지 않는다. 거기에 복잡한 쿼리를 이름 붙여 저장하는 VIEW, DB를 코드에서 다루는 Python sqlite3 연동까지. 관통하는 메시지는 어제와 같다 — DB마다 문법 지원이 다르다(슬라이드의 표준/Oracle ALL/ANY·DUAL·CREATE OR REPLACE VIEW vs SQLite의 MAX/MIN·FROM 생략·DROP+CREATE). 다음 시간엔 윈도우 함수다.
