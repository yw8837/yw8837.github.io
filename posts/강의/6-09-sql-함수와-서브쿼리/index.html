어제(6/8) SELECT로 데이터를 골라봤다면, 오늘은 그 위에 네 개의 무기를 얹었다 — 집계함수(여러 행을 한 값으로 요약), GROUP BY(그룹별 집계), JOIN(여러 테이블 결합), 서브쿼리(쿼리 속 쿼리). 난도가 확 올라가는 날이라, 강사님은 **“분할 → 각각 실행 → 합치기”**라는 학습법을 계속 강조했다.

📖 수업 내용#

오늘의 흐름은 이렇다.

  1. 집계 함수 — COUNT·SUM·AVG·MAX·MIN으로 여러 행을 한 값으로 요약
  2. GROUP BY / HAVING — “그룹별로 묶어서” 집계하고, 그 결과에 조건 걸기
  3. JOIN — 흩어진 여러 테이블을 키로 연결 (INNER·LEFT·RIGHT)
  4. 서브쿼리 — 쿼리 안에 또 다른 쿼리를 넣어 “모르는 기준"으로 검색

01 · 집계 함수 — 여러 행을 한 값으로#

지금까지 SELECT는 행을 그대로 여러 줄 보여줬다. **집계 함수(Aggregate Function)**는 여러 행을 하나의 요약값으로 만든다. 다섯 가지를 배웠다.

함수 하는 일 비유
COUNT 개수 세기 “몇 명?”
SUM 합계 “다 더하면?”
AVG 평균 “평균은?”
MAX 최댓값 “제일 큰 값?”
MIN 최솟값 “제일 작은 값?”

COUNT#

COUNT는 검색 결과의 데이터 개수를 센다. 한 가지 중요한 특징 — NULL(빈 값)은 세지 않는다.

SELECT COUNT(id) FROM book;   -- id 컬럼의 값 개수 (NULL 제외)
SELECT COUNT(*)  FROM book;   -- 전체 행 개수

💡 팁: 전체 10행 중 어떤 컬럼에 NULL이 3개 있으면 COUNT(그 컬럼)은 7이 나온다. “왜 개수가 적지?” 싶으면 NULL을 의심하자. 그래서 행 전체를 셀 땐 COUNT(*)를 쓴다.

SUM · AVG · MAX · MIN#

SELECT SUM(math) FROM grade;                          -- 합계
SELECT AVG(korean), AVG(english), AVG(math) FROM grade; -- 평균(여러 개 동시 가능)
SELECT MAX(korean) FROM grade;                        -- 최댓값
SELECT MIN(english) FROM grade;                       -- 최솟값

AVG는 SUM/COUNT를 직접 안 써도 평균을 구해준다. MAX·MIN은 숫자뿐 아니라 문자형에도 쓸 수 있다(알파벳 순 최대/최소).

LIMIT 다시 보기#

LIMIT는 출력 개수를 제한한다. 인덱스 시작이 0이라는 점이 포인트다.

SELECT * FROM book LIMIT 5;     -- 앞에서 5개
SELECT * FROM book LIMIT 1, 5;  -- 2번째부터 5개 (시작 인덱스 1 = 두 번째)

💡 팁: LIMIT는 DBMS마다 문법이 다르다. 예를 들어 Oracle은 문법이 상이하다. “환경마다 다를 수 있다"를 항상 기억하자.

02 · GROUP BY / HAVING — 그룹별로 묶어 집계하기#

집계 함수를 그룹별로 쓰고 싶을 때가 있다. “나라별 고객 수”, “장르별 평균 재생시간"처럼. 이때 **GROUP BY**를 쓴다.

SELECT user_id, COUNT(*)
FROM rental
GROUP BY user_id;   -- user_id가 같은 것끼리 묶어서 각 그룹의 개수

기준 컬럼이 같은 행끼리 묶고, 그 그룹마다 집계 함수(COUNT/SUM/AVG/MAX/MIN)를 적용한다.

💡 팁: GROUP BY의 기준 컬럼은 SELECT 절에도 반드시 넣는 게 원칙이다. SQLite는 안 넣어도 동작하는 경우가 있지만, 결과의 의미가 불명확해지므로 정석 문법을 지키자.

HAVING — 그룹에 조건 걸기#

WHERE는 그룹으로 묶기 전 개별 행을 거르고, HAVING은 그룹으로 묶은 후 그룹을 거른다.

SELECT user_id, COUNT(*)
FROM rental
GROUP BY user_id
HAVING COUNT(user_id) > 1;   -- 묶은 결과 중 개수가 1보다 큰 그룹만
절 거르는 시점 대상
WHERE 그룹화 전 개별 행
HAVING 그룹화 후 그룹(집계 결과)

💡 팁: HAVING은 혼자 못 쓴다. 반드시 GROUP BY 다음에 온다. “집계한 결과에 조건"이 필요할 때 HAVING을 떠올리자.

예를 들어 chinook에서 “앨범이 5개 이상인 아티스트만"은 이렇게 쓴다(노션 실제 답지 — 지문은 “5개 이상"이나 답지 SQL은 > 5로 작성돼 있다).

SELECT ArtistId, COUNT(*) AS album_cnt FROM albums
GROUP BY ArtistId
HAVING COUNT(*) > 5;

03 · JOIN — 흩어진 테이블을 연결하기#

데이터는 보통 여러 테이블에 나뉘어 저장된다. 왜 나눌까?

  • 중복·저장 낭비 방지 (같은 정보를 여기저기 적지 않음)
  • 수정의 일관성 (유저 정보 한 번만 고치면 됨)
  • 삭제·무결성 문제 방지

이렇게 잘 나누는 설계를 정규화라 한다(자세한 건 후반부). 그런데 나눠놓으면 합쳐서 봐야 할 때가 온다. 그게 JOIN이다.

INNER JOIN — 교집합#

두 테이블에서 키가 서로 매칭되는 행만 가져온다(교집합).

SELECT *
FROM rental
INNER JOIN user
ON user.id = rental.user_id;   -- 두 테이블을 잇는 '키'를 ON으로 지정

매칭되지 않는 행(예: 대여 기록이 없는 유저)은 결과에서 빠진다.

💡 팁: ERD를 보고 어떤 키로 연결되는지 먼저 확인하라. 그리고 두 테이블에 같은 컬럼명(예: Name)이 있으면 table.column으로 명시해야 한다. 안 그러면 ambiguous column name(컬럼 이름이 모호함) 오류가 난다.

3개 테이블도 연결할 수 있다. 단, 직접 연결되는 키가 있어야 한다. 예를 들어 트랙→아티스트는 직접 연결이 안 돼서, 앨범을 경유해야 한다(트랙→앨범→아티스트).

SELECT tracks.Name, albums.Title, artists.Name
FROM tracks
INNER JOIN albums  ON tracks.AlbumId  = albums.AlbumId
INNER JOIN artists ON albums.ArtistId = artists.ArtistId
LIMIT 20;

💡 팁: 조인이 잘 됐는지 먼저 SELECT *로 확인한 뒤, 필요한 컬럼만 좁히는 게 실습 요령이다. 단, 실무에서 SELECT *는 금지에 가깝다(컬럼 과다·성능·가독성). 확인용으로만 쓰자.

LEFT JOIN / RIGHT JOIN — 한쪽을 다 보존#

종류 결과
INNER JOIN 양쪽 다 매칭되는 것만 (교집합)
LEFT JOIN 왼쪽 테이블 전부 + 매칭 안 되면 NULL
RIGHT JOIN 오른쪽 테이블 전부 + 매칭 안 되면 NULL 
SELECT * FROM user LEFT  JOIN rental ON user.id = rental.user_id;  -- user 전부
SELECT * FROM user RIGHT JOIN rental ON user.id = rental.user_id;  -- rental 전부

NULL 필터링 — “관계 없는 행” 찾기#

LEFT JOIN으로 “앨범이 하나도 없는 아티스트” 같은 걸 찾을 수 있다. 매칭 실패 시 NULL이 되니, 그 NULL을 거르면 된다.

SELECT artists.Name
FROM artists LEFT JOIN albums ON artists.ArtistId = albums.ArtistId
WHERE albums.AlbumId IS NULL;   -- 앨범이 없는(매칭 실패) 아티스트만

💡 팁: NULL은 = NULL로 못 거른다. 반드시 **IS NULL / IS NOT NULL**을 써야 한다. “관계가 없는 행 찾기"의 핵심 기술이다.

💡 팁: RIGHT JOIN보다 LEFT JOIN을 권장한다. 두 테이블이면 테이블 순서만 바꾸면 RIGHT 효과를 LEFT로 낼 수 있기 때문. 게다가 RIGHT JOIN은 SQLite 3.39.0 이상에서만 동작한다.

참고: 강사님은 Customer.SupportRepId 같은 컬럼은 이름만 봐선 의미를 알기 어렵다며, **데이터 정의서(Data Dictionary)**가 있으면 “SupportRepId = 담당 직원 EmployeeId"를 추론 없이 확인할 수 있다고 강조했다.

04 · 서브쿼리 — 쿼리 속의 쿼리#

서브쿼리는 **“하나의 쿼리 안에 포함된 또 하나의 쿼리”**다. 메인쿼리가 서브쿼리를 품는 종속 관계다.

왜 쓸까? 기준값을 모를 때 유용하다. 예를 들어 “elice보다 급여 높은 사람"을 찾는데 elice 급여를 모른다면:

-- 급여 2500을 '아는' 상태라면:
SELECT * FROM employee WHERE 급여 > 2500;

-- 급여를 '몰라도' 서브쿼리로:
SELECT * FROM employee
WHERE 급여 > (SELECT 급여 FROM employee WHERE 이름 = 'elice');

주의사항 4가지 (슬라이드):

  1. 서브쿼리는 괄호 ()와 함께 쓴다.
  2. 서브쿼리 안에서는 ORDER BY 사용 불가.
  3. 서브쿼리는 연산자의 오른쪽에 둔다.
  4. 서브쿼리는 오직 SELECT문으로만 작성한다.

💡 핵심 학습법(강사님 반복 강조): “분할 → 각각 실행 → 합치기”. 메인쿼리와 서브쿼리를 먼저 텍스트로 구분하고, 바로 코딩하지 말고 구조부터 잡는다. 각각 따로 돌려보고 맞으면 합친다.

단일행 vs 다중행 서브쿼리#

서브쿼리가 몇 개의 값을 돌려주느냐로 나뉜다.

종류 반환 쓰는 연산자
단일행 1개 값 =, <>, >, >=, <, <=
다중행 2개 이상 IN, ANY, ALL 
-- 단일행: 평균보다 긴 트랙 (AVG는 값 1개)
SELECT Name FROM tracks
WHERE Milliseconds > (SELECT AVG(Milliseconds) FROM tracks);

-- 다중행: 부서별 최고 급여에 해당하는 사람 (여러 부서 = 여러 값)
SELECT * FROM employee
WHERE 급여 IN (SELECT MAX(급여) FROM employee GROUP BY 부서번호);

⚠️ SQLite 주의: SQLite는 ANY/ALL을 지원하지 않는다. 대신 MIN/MAX로 대체한다.

  • ALL(모든 값보다 큼) → MAX보다 큼
  • ANY(하나라도보다 큼) → MIN보다 큼

위치에 따른 분류#

서브쿼리가 쿼리의 어디에 들어가느냐로도 나뉜다.

위치 이름 특징
WHERE 절 가장 일반적 조건에 서브쿼리
SELECT 절 스칼라 서브쿼리 한 행만 반환, JOIN과 같은 결과
FROM 절 파생 테이블 서브쿼리 결과를 표처럼 사용, 별칭 필수
EXISTS 상관 서브쿼리 존재 여부만 확인 
-- 스칼라(SELECT절): 앨범별 트랙 수
SELECT a.Title, (SELECT COUNT(*) FROM tracks t WHERE t.AlbumId = a.AlbumId) AS track_count
FROM albums a;

-- FROM절 파생 테이블: 앨범별 트랙 수의 전체 평균 (별칭 sub 필수)
SELECT AVG(cnt) FROM (
    SELECT AlbumId, COUNT(*) AS cnt FROM tracks GROUP BY AlbumId
) AS sub;

-- EXISTS: 트랙이 있는 앨범만
SELECT Title FROM albums a
WHERE EXISTS (SELECT 1 FROM tracks t WHERE t.AlbumId = a.AlbumId);

💡 팁: NOT IN은 NULL에 취약하다. 서브쿼리 결과에 NULL이 섞이면 아무것도 반환 안 할 수 있다. 그래서 “구매 안 된 트랙 찾기” 같은 건 NOT EXISTS가 더 안전하다(NULL 안전).

05 · 강사님이 강조한 포인트 (정리)#

  • 서브쿼리 핵심 학습법: “분할 → 각각 실행 → 합치기”. 바로 코딩 말고 구조부터.
  • GROUP BY 기준 컬럼은 SELECT에도 포함(정석). SQLite가 예외 동작해도 정석 준수.
  • JOIN은 ERD/키 확인 후 작성. 컬럼명 겹치면 table.column, 동일 컬럼명은 별칭으로 구분.
  • SELECT *는 실무에서 금지에 가까움. 조인 확인용으로만.
  • RIGHT JOIN보다 LEFT JOIN 권장(테이블 순서로 대체). RIGHT는 SQLite 3.39.0+ 필요.
  • NULL 필터링은 IS NULL/IS NOT NULL. 비교 연산으로는 NULL을 못 거른다.
  • NOT IN은 NULL 취약 → NOT EXISTS가 안전.
  • SQLite는 ANY/ALL 미지원 → MIN/MAX로 대체.
  • COUNT는 NULL 제외, 용어 “컬럼=필드” 혼용 주의.
  • 분석가 로드맵: 기본문법 + 서브쿼리 + 조인 + 윈도우 함수, 그리고 보고서·엑셀 역량도 중요.
  • 운영: 시험은 classicmodels DB로 진행 예고. 답지는 노션 업로드.

마무리#

오늘은 SELECT 위에 집계·그룹·결합·중첩을 쌓은 날이다. 집계 함수로 여러 행을 한 값으로 요약하고, GROUP BY/HAVING으로 그룹별로 집계·필터하고, JOIN으로 흩어진 테이블을 키로 잇고, 서브쿼리로 모르는 기준까지 검색했다. 양이 많지만 관통하는 학습법은 하나다 — “분할 → 각각 실행 → 합치기”. 복잡한 쿼리일수록 한 번에 쓰려 하지 말고, 조각으로 나눠 각각 검증한 뒤 합치자. 그리고 SQLite의 특이점(ANY/ALL 미지원, RIGHT JOIN 버전 제약)과 NULL의 함정(NOT IN vs NOT EXISTS)을 꼭 기억하자.
