01 · 관계형 대수 — SQL 연산의 뿌리#

오늘 배울 집합 연산자가 어디서 왔는지부터 짚자. 관계형 대수(Relational Algebra) 는 관계형 DB에서 원하는 정보를 유도하기 위한 기본 연산 묶음이다. 크게 두 갈래다.

갈래 연산 SQL에서는
일반 집합 연산 합집합(∪) UNION
교집합(∩) INTERSECT
차집합(−) EXCEPT (Oracle은 MINUS)
카티션 곱(×) CROSS JOIN
순수 관계 연산 셀렉션(σ) — 행 필터 WHERE
프로젝션(∏) — 열 선택 SELECT
조인(Join) 각종 JOIN
디비전(÷) (직접 키워드 없음)

[원문 슬라이드 도식 참조: A∪B / A∩B / A−B 벤다이어그램]

쉽게 말해, 우리가 매일 쓰는 SELECT(프로젝션)와 WHERE(셀렉션)도 사실은 이 관계형 대수 연산에 이름표가 붙은 것이다. 오늘 주인공인 집합 연산자 3종(UNION/INTERSECT/EXCEPT) 은 “일반 집합 연산"에 해당한다.

💡 팁: 카티션 곱(CROSS JOIN) 은 집합 연산자가 아니라 JOIN 단원에서 따로 다룬다. 그리고 디비전은 강사님이 “현업에서 거의 안 쓴다"고 했으니, 이런 게 있다 정도만 알고 넘어가면 된다. 시험·면접에서 중요한 건 합·교·차다.

02 · 집합 연산자란 — 조인 없이 결과를 세로로 합치기#

집합 연산자(Set Operator) 는 두 개 이상의 SELECT 결과를 조인을 쓰지 않고 하나로 묶는 방법이다. JOIN이 테이블을 가로로(컬럼을 늘려) 붙인다면, 집합 연산자는 세로로(행을 쌓아) 합치거나 빼낸다고 생각하면 직관적이다.

대신 지켜야 할 공통 규칙이 있다. 두 SELECT의 모양이 맞아야 한다.

규칙 내용
① 컬럼 수 일치 두 SELECT의 컬럼 개수가 같아야 한다
② 데이터 타입 호환 같은 자리(1번↔1번)의 컬럼 타입이 호환돼야 한다
③ 컬럼명 최종 결과의 컬럼명은 첫 번째 SELECT의 것을 따른다
④ ORDER BY 정렬은 개별 SELECT가 아니라 최종 결합 결과에만 한 번 적용

종류는 네 가지다. 차이는 “중복을 제거하느냐"와 “정렬을 하느냐"로 갈린다.

연산자 역할 중복 제거 정렬 발생
UNION 합집합 O O
UNION ALL 합집합(중복 포함) X X (그래서 빠름)
INTERSECT 교집합 O O
EXCEPT 차집합(앞 − 뒤) O O

💡 팁: 컬럼 수가 안 맞으면 “SELECT의 결과 컬럼 수가 다르다"는 오류가 난다. 집합 연산이 안 될 땐 두 SELECT의 컬럼 개수부터 세어 보자.

UNION (합집합)#

두 결과를 합치되 중복 행은 제거한다. 중복을 가려내려면 내부적으로 정렬을 한 번 거치는데, 그렇다고 우리가 원하는 순서로 나오는 건 아니다. 보기 좋게 정렬하려면 맨 끝에 ORDER BY 를 직접 붙여야 한다.

SELECT * FROM ALPHA
UNION
SELECT * FROM BETA;   -- 두 테이블을 합치고 중복은 1번만 남김

실무 예시는 “직원 + 고객을 한 명단으로 합치기"다. 이때 'Employee' / 'Customer' 같은 상수 컬럼을 끼워 넣어 “이 행이 어느 쪽에서 왔는지"를 표시하는 게 흔한 기법이다(코드 노트 01 참고).

UNION ALL (합집합, 중복 포함)#

UNION과 거의 같지만 중복 제거도, 정렬도 하지 않는다. “중복을 제거하지 않는다"가 가장 중요한 차이다. 그래서 더 빠르다.

💡 팁: 중복이 없다고 확신하거나, 중복까지 그대로 보고 싶을 땐 UNION ALL이 정답이다. 괜히 UNION을 쓰면 불필요한 정렬·중복 제거 비용만 든다. “중복 제거가 꼭 필요한가?“를 먼저 묻고 아니면 UNION ALL.

INTERSECT (교집합)#

두 결과에서 겹치는 행만 남긴다(중복은 제거). “양쪽에 다 있는 것"이다.

SELECT A, B FROM ALPHA
INTERSECT
SELECT A, B FROM BETA;   -- 양쪽 모두에 등장하는 행만

예: “2009년에도 사고 2010년에도 산 고객” = 2009년 구매자 ∩ 2010년 구매자.

EXCEPT (차집합 = Oracle의 MINUS)#

앞 결과에서 뒤 결과에 있는 것을 빼낸다(중복 제거). 마케팅으로 치면 “이탈 고객” 같은 개념이다 — “작년엔 샀는데 올해는 안 산 사람” = 작년 구매자 − 올해 구매자.

SELECT A, B FROM ALPHA
EXCEPT
SELECT A, B FROM BETA;   -- ALPHA에는 있고 BETA엔 없는 행

🚨 여기서 DBMS 차이가 결정적이다#

이론은 Oracle/MariaDB 기준인데, 같은 키워드라도 DB마다 지원이 다르다. 실무에서 “왜 내 쿼리가 에러나지?“의 단골 원인이라 표로 정리한다.

연산 Oracle MariaDB MySQL SQLite (오늘 실습)
UNION / UNION ALL O O O O
INTERSECT O O X (미지원) O
EXCEPT MINUS 라는 이름 O (10.3+) X (미지원) O

💡 실무 주의: MySQL은 INTERSECT·EXCEPT를 지원하지 않는다. MySQL 환경이라면 교집합/차집합을 JOIN이나 IN/NOT IN/NOT EXISTS로 우회해야 한다. 또 차집합은 Oracle에선 EXCEPT가 아니라 MINUS 다. 이름만 다를 뿐 역할은 같다. “이 DB가 이 연산자를 지원하나?“를 먼저 확인하는 습관을 들이자.

참고(데이터 특이사항): 오늘 실습 DB인 Chinook은 고객과 청구서가 거의 1:1로 매칭돼 있어, “청구서 없는 고객"을 EXCEPT로 뽑으면 결과가 거의 비어 보일 수 있다. 쿼리가 틀린 게 아니라 데이터 특성이니 당황하지 말자(강사님 언급).

03 · 집계 + 집합 연산 응용 — “소계 행” 붙이기#

집합 연산자가 빛나는 실무 패턴 하나가 소계(subtotal) 리포트다. 엑셀에서 표 맨 아래에 “합계” 행을 붙이듯, 그룹별 집계 결과 + 전체 합계 행을 한 표에 담는 것이다.

방법은 간단하다. ① 그룹별 집계 쿼리와 ② 전체 합계 쿼리를 각각 만든 뒤, UNION ALL로 세로로 이어 붙인다.

-- 연도별 매출
SELECT strftime('%Y', InvoiceDate) AS 연도, ROUND(SUM(Total), 2) AS 매출합계
FROM invoices GROUP BY 연도
UNION ALL
-- 맨 아래 '전체합계' 행
SELECT '── 전체합계', ROUND(SUM(Total), 2) FROM invoices
ORDER BY 연도;

여기서 합계 행은 '── 전체합계' 같은 문자열을 연도 자리에 박아 구분한다. 중복이 생길 일이 없으니 UNION ALL(중복 제거 불필요)을 쓰는 게 자연스럽다.

💡 팁: 강사님은 이 패턴을 만들 때 “개별 쿼리(연도별 / 전체)를 각각 먼저 실행해 확인한 뒤 합친다” 고 강조했다. 어제 배운 “분할 → 각각 실행 → 합치기” 가 집합 연산에서도 그대로 통한다. 한 번에 다 쓰지 말고 조각으로 검증하자.

💡 실무 응용: INTERSECT/EXCEPT 결과(예: “2009·2010 둘 다 산 고객 ID”)는 그 자체로는 ID 목록일 뿐이다. 이걸 FROM절 서브쿼리(인라인 뷰)처럼 감싸 customers와 JOIN 하면 이름까지 붙은 완성된 리포트가 된다(코드 노트 04·05 참고). 어제 배운 서브쿼리·조인과 자연스럽게 이어진다.

04 · 계층형 질의 — 조직도처럼 상하 관계 파고들기#

계층형 데이터란#

계층형 데이터(Hierarchical Data) 는 같은 테이블 안에서 행들끼리 상하(부모-자식) 관계를 갖는 구조다. 대표 예가 직원-관리자다. employees 테이블의 한 직원이 다른 직원(관리자)을 가리키고, 그 관리자도 또 위의 관리자를 가리킨다. 마치 회사 조직도, 또는 카테고리 > 하위 카테고리 트리처럼.

        (Root: 관리자 없음)
            CEO
           /   \
        팀장A   팀장B
        /  \
     사원1  사원2   ← Leaf(부하 없음)

[원문 슬라이드 도식 참조: 계층 트리 p25]

Chinook의 employees 테이블이 딱 이 구조다. EmployeeId 가 자기 번호, ReportsTo 가 “내 관리자의 EmployeeId"다. ReportsTo가 NULL이면 최상위(Root), 즉 위에 보고할 사람이 없는 사람이다.

🚨 여기서도 DBMS가 갈린다 — CONNECT BY vs WITH RECURSIVE#

계층을 펼치는 문법은 DB 계열마다 완전히 다르다. 이게 오늘 가장 중요한 대비 포인트다.

방식 지원 DB 키워드
CONNECT BY Oracle START WITH + CONNECT BY PRIOR
재귀 CTE SQL Server(2005+), MariaDB(10.2+), SQLite WITH RECURSIVE

(1) Oracle 방식 — CONNECT BY#

Oracle은 계층 전용 문법을 제공한다. START WITH로 루트를 정하고, CONNECT BY PRIOR로 상위↔하위를 연결한다.

SELECT LEVEL, 사원번호, 관리자
FROM 직원
START WITH 관리자 IS NULL              -- 루트: 관리자가 없는 사람부터
CONNECT BY PRIOR 사원번호 = 관리자;     -- 상위(PRIOR 사원번호) = 하위의 관리자

Oracle은 계층을 다루는 편의 키워드도 많다.

키워드 의미
LEVEL 깊이(루트=1)
CONNECT_BY_ROOT 현재 행의 최상위(루트) 값
CONNECT_BY_ISLEAF 리프(최하위)면 1, 아니면 0
SYS_CONNECT_BY_PATH(컬럼, 구분자) 루트부터 현재까지의 경로

💡 팁: LPAD(' ', 4*(LEVEL-1)) 처럼 LEVEL에 비례해 공백을 넣으면 결과가 조직도처럼 들여쓰기돼 보인다. 루트는 LEVEL=1이라 4*(1-1)=0, 즉 들여쓰기 없음.

(2) 표준/SQLite 방식 — 재귀 CTE (WITH RECURSIVE)#

SQLite는 CONNECT BY를 지원하지 않는다. 대신 표준 SQL의 재귀 CTE(WITH RECURSIVE) 를 쓴다. SQL Server·MariaDB·MySQL 8+도 이 방식이다. 구조는 세 부분이다.

WITH RECURSIVE CTE(member_id, manager_id, lvl) AS (
    -- ① 앵커(Anchor): 출발점 = 루트
    SELECT member_id, manager_id, 0 AS lvl
    FROM MEMBER
    WHERE manager_id IS NULL

    UNION ALL                          -- ② 앵커와 재귀를 잇는 다리

    -- ③ 재귀(Recursive): 바로 아래 부하를 찾아 lvl+1
    SELECT a.member_id, a.manager_id, b.lvl + 1
    FROM MEMBER a
    JOIN CTE AS b ON a.manager_id = b.member_id
)
SELECT member_id, manager_id, lvl
FROM CTE
ORDER BY member_id, lvl;

동작 원리를 한 문장으로: 루트에서 시작(앵커, lvl=0) → 매 순환마다 “방금 찾은 사람의 직속 부하"를 찾아 lvl을 1씩 늘리며 누적 → 더 찾을 부하가 없으면 멈춘다. 슬라이드는 이 순환을 1·2·3·4단계 테이블이 점점 쌓이는 그림으로 보여줬다. [원문 슬라이드 도식 참조: p34~42 순환 단계별 테이블]

💡 팁: 재귀 CTE를 처음 보면 “닭이 먼저냐 달걀이 먼저냐” 같지만, 앵커(루트)가 달걀이다. 앵커가 먼저 한 줄을 깔아주고, 재귀 부분이 그 위에 한 층씩 쌓는다. UNION ALL이 “앵커 결과 + 재귀 결과"를 계속 합쳐 주는 접착제 역할이다.

💡 실무 주의: 재귀 CTE는 종료 조건(더 매칭될 자식이 없음) 이 자연스럽게 보장되지만, 데이터에 순환 참조(A→B→A)가 있으면 무한 루프에 빠질 수 있다. 실무 계층 데이터에선 순환이 없도록 설계·검증하는 게 중요하다.

참고: 이렇게 펼친 계층 결과에 어제 배운 집계·조인을 얹으면 “직원별 담당 고객 수·매출”(계층 + GROUP BY + JOIN)이나 “레벨별 인원수 + 합계”(계층 + UNION ALL 소계) 같은 리포트로 확장된다(코드 노트 06 참고). 들여쓰기는 SUBSTR(' ', 1, lvl*4)로 흉내 내는데, 환경에 따라 의도대로 안 보일 수 있다고 강사님이 덧붙였다.

05 · 강사님이 강조한 포인트 (정리)#

  • 집합 연산자 = 조인 없이 결과를 세로로 합치기/빼기. 공통 규칙(컬럼 수·타입 호환·첫 쿼리 컬럼명·ORDER BY는 최종만)부터.
  • UNION vs UNION ALL의 핵심 차이는 “중복 제거 여부”. 중복 제거가 불필요하면 더 빠른 UNION ALL.
  • DBMS 차이 필수 암기: MySQL은 INTERSECT·EXCEPT 미지원, 차집합은 Oracle에서 MINUS.
  • 소계 리포트 = 그룹 집계 + 전체 합계 쿼리를 UNION ALL로 결합(엑셀 합계 행).
  • 집합 연산 결과를 서브쿼리로 감싸 JOIN 하면 ID만 있던 결과에 이름까지 붙는다.
  • 계층형 질의는 같은 테이블의 상하 관계(직원-관리자). 루트 = 부모가 NULL인 행.
  • Oracle은 CONNECT BY, 표준/SQLite는 WITH RECURSIVE. SQLite엔 CONNECT BY 없음.
  • 재귀 CTE 3요소: 앵커(루트) + UNION ALL + 재귀(자식 탐색, lvl+1).
  • 여전히 통하는 학습법: “분할 → 각각 실행 → 합치기”. 복잡한 쿼리일수록 조각으로 검증.

마무리#

오늘은 데이터를 다루는 두 개의 새 시야를 얻었다. 집합 연산자로는 조인 없이 두 결과를 세로로 합치거나(UNION·UNION ALL) 겹치는 부분만 남기거나(INTERSECT) 빼낼(EXCEPT) 수 있게 됐고, 엑셀 같은 소계 리포트도 UNION ALL로 만들 수 있었다. 계층형 질의로는 조직도처럼 같은 테이블 안의 상하 관계를 재귀로 펼쳐, 누가 누구의 부하인지·몇 단계 깊이인지·전체 경로까지 뽑아냈다. 관통하는 메시지는 두 가지다 — 하나는 “DB마다 문법 지원이 다르다”(MySQL의 INTERSECT/EXCEPT 미지원, Oracle CONNECT BY vs 표준 WITH RECURSIVE), 다른 하나는 여전히 유효한 “분할 → 각각 실행 → 합치기”. 복잡해 보이는 재귀 CTE도 결국 앵커 한 줄에서 시작해 한 층씩 쌓는 것뿐이다.
