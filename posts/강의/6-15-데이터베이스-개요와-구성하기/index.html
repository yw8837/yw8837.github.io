01 · DB는 왜 필요한가 — 파일처리 시스템의 한계#

먼저 용어 정리부터. 데이터(data) 는 현실에서 수집한 가공 전의 단순한 사실·값이다(예: 85, 홍길동). 정보(information) 는 그 데이터를 목적에 맞게 의미 있게 가공한 결과다(예: “홍길동의 점수 85점은 상위 10%”). 그리고 데이터베이스(DB) 는 한 조직 안에서 여러 사용자·프로그램이 공유하려고 통합·저장·운영하는 데이터의 집합이다.

그럼 그냥 엑셀 파일이나 CSV에 저장하면 안 될까? 강사님은 “개인 작업이라면 엑셀·CSV·SQLite로도 충분하다"고 했다. 문제는 조직 단위로 갈 때 생긴다. 예전 방식(파일처리 시스템)은 세 가지 한계가 있다.

한계 무슨 뜻인가 쉬운 비유
데이터 종속성 데이터 구조가 바뀌면 그 데이터를 쓰는 프로그램도 다 같이 고쳐야 함 책장 칸 배치를 바꿨더니, 그 책장을 쓰는 모든 사람이 위치를 새로 외워야 하는 격
데이터 중복성 프로그램마다 같은 데이터를 따로 복사해 보관 → 중복 같은 연락처를 카톡·전화부·메모장에 각각 저장
무결성 훼손 중복된 데이터가 서로 안 맞게 되어 어디가 맞는지 모름 카톡엔 010-1111, 전화부엔 010-2222

💡 그래서 DB는 공유 · 동시 사용 · 권한 관리 · 무결성을 한 곳에서 책임진다. 이게 “왜 DB인가"의 답이다.

⚠️ 팀 프로젝트에서 SQLite 쓰지 말 것(강사 경고). SQLite는 파일 하나로 된 개인용 DB라 여러 명이 동시에 쓰는 팀 프로젝트엔 부적절하다 → 팀은 클라우드 DB를 권장한다. (단 오늘 실습은 학습 목적이라 가볍게 SQLite를 쓴다.)

02 · DB의 종류 — RDB vs NoSQL#

DB는 크게 두 갈래다. 데이터를 표(table) 로 다루는 관계형(RDB) 과, 표 틀에 얽매이지 않는 NoSQL.

구분 RDB (관계형) NoSQL (Not only SQL)
데이터 구조 2차원 표(행·열), 정해진 스키마 유연한 스키마(미리 정의 안 함)
강점 무결성·일관성·신뢰성, 정규화로 중복 최소화 비정형 데이터(이미지·자연어), 대용량·수평 확장
어울리는 상황 구조가 일관적이고 정확성이 중요할 때 구조가 자주 바뀌거나 대량을 빠르게 처리할 때
대표 제품 MySQL, PostgreSQL, MariaDB, Oracle MongoDB, Redis, Cassandra

RDB는 데이터를 행과 열의 표로 표현하고, 표끼리 관계로 이어 무결성을 지킨다. 구조가 일관적이라 신뢰성·안정성이 높다. NoSQL은 미리 정한 스키마가 없어 자유롭게 저장할 수 있고, 비정형 데이터나 대용량 분산 저장에 강하다.

💡 강사 선택 팁: “분석에 어떤 DB를 쓸 것인가"의 선택이 중요하다. NoSQL은 폭넓게 저장 가능하지만 학습 난이도가 있고, 공간(지도) 데이터는 PostgreSQL을 추천한다. 현업 분석에선 클라우드 데이터 웨어하우스(BigQuery 등) 사용 빈도가 높다(쿠팡 등 사례). 클라우드는 비용이 드니 용도·예산을 함께 고려한다.

03 · 관계형 DB 만들기 — CREATE / INSERT / SELECT#

이제 표를 직접 만든다. 그 전에 RDB 용어부터 — 같은 것을 부르는 이름이 여러 개라 헷갈리기 쉽다.

표현 1 표현 2 표현 3 쉬운 설명
행(row) 튜플(tuple) 레코드 가로 한 줄 = 데이터 한 건
열(column) 속성(attribute) — 세로 한 칸 = 항목(이름, 나이…)
기본키(PK) — — 행을 유일하게 식별하는 속성(예: id)
도메인(domain) — — 그 속성이 가질 수 있는 값의 범위

기본 구문 세 개다. (아래는 슬라이드의 일반형 틀 — ⚠ 일반형)

-- 테이블 만들기
CREATE TABLE 테이블명 (속성1 데이터타입, 속성2 데이터타입, ...);

-- 데이터 넣기 (속성 생략 시 빈 칸엔 NULL이 들어감)
INSERT INTO 테이블명 (속성1, 속성2, ...) VALUES (값1, 값2, ...);

-- 데이터 꺼내기
SELECT 속성1, 속성2, ... FROM 테이블명;

💡 SQL 작성 규칙(가독성 약속):

  • 키워드(CREATE, SELECT…)는 대문자
  • 테이블·속성 이름은 소문자, 띄어쓰기는 언더바(_)로 (dept_name)
  • 이름은 의미가 분명하게, 명령 끝엔 세미콜론(;)

04 · SQL 3분류 · 자료형 · ALTER / DROP#

SQL(Structured Query Language)은 관계형 DB를 다루는 표준 언어다. 하는 일에 따라 세 종류로 나뉜다.

분류 풀이 하는 일 대표 명령
DDL 데이터 정의어 테이블 등 구조를 정의 CREATE, ALTER, DROP
DML 데이터 조작어 데이터를 조회·입력·수정·삭제 SELECT, INSERT, UPDATE, DELETE
DCL 데이터 제어어 권한을 부여·회수 GRANT, REVOKE

지금까지 우리가 쓰던 SELECT는 DML, 오늘 새로 배우는 CREATE는 DDL이다.

자료형 — 칸마다 담는 값의 종류#

테이블을 만들 땐 각 칸에 무슨 종류의 값이 들어갈지(자료형)를 정해야 한다. DBMS마다 종류·이름이 조금씩 다르다.

자료형 설명
VARCHAR(n) 최대 n바이트의 가변 길이 문자
INT 정수(4바이트)
FLOAT 실수, 4바이트 부동소수점
DATETIME 날짜+시간 (YYYY-MM-DD HH:MM:SS)

💡 강사 포인트: VARCHAR 길이 같은 건 확장성을 고려해 정한다(다국적 이름, 긴 입력 등). 화면 입력(문자열) → 앱 처리 → DB 저장(날짜 타입 등) 사이에 타입이 안 맞아 정보가 유실될 수 있다는 점도 주의. 그리고 어떤 칸을 필수로 할지(NOT NULL), 기본값을 줄지(DEFAULT)는 비즈니스 로직에 근거해 설계해야 한다 → 바로 다음 챕터 제약조건으로 이어진다.

테이블 수정·삭제 — ALTER / DROP#

-- 슬라이드 일반형(⚠ MySQL 기준)
ALTER TABLE 테이블명 ADD COLUMN 컬럼명 데이터타입;     -- 컬럼 추가
ALTER TABLE 테이블명 MODIFY COLUMN 컬럼명 데이터타입;  -- 컬럼 수정
ALTER TABLE 테이블명 DROP COLUMN 컬럼명;               -- 컬럼 삭제
DROP TABLE 테이블명;                                   -- 테이블 통째 삭제

⚠️ SQLite 주의: 위 MODIFY COLUMN·CHANGE COLUMN은 MySQL 문법이라 SQLite에선 안 된다. SQLite의 ALTER는 ADD COLUMN 정도만 되고, 제약·기본값을 바꾸려면 새 테이블을 만들어 데이터를 복사한 뒤 이름을 바꾸는 우회 패턴을 쓴다(코드 노트 참고).

💡 DROP 순서(강사): 외래키(FK)로 연결된 테이블은 참조 역순(자식 → 부모) 으로 지워야 에러가 안 난다. 부모를 먼저 지우면 “아직 자식이 참조 중인데?” 하고 막힌다.

05 · 제약조건 — “잘못된 데이터를 막는 마지막 방어선”#

오늘의 핵심. 제약조건(constraint) 은 정확한 데이터만 들어오도록 보장하는 규칙이다. 비즈니스 규칙을 DB 레벨에서 강제해, 프론트엔드·백엔드가 실수로 이상한 값을 보내도 DB가 마지막에 막아준다. 그래서 강사님은 이를 “마지막 방어선” 이라 불렀다.

왜 유용한가? ① DB 관리자 관점: 무결성 유지 ② 비즈니스 관점: 규칙 강제(예: 19세 미만 가입 차단) ③ 분석·개발 관점: 쓰레기 데이터가 줄어 정제 비용이 줄고 양질의 데이터가 쌓인다.

제약조건 하는 일 한 줄 예시
NOT NULL 빈 값(NULL) 금지 = “필수 입력” 이름은 반드시 있어야 함
UNIQUE 중복 값 금지 (단 NULL은 중복 허용) 이메일은 겹치면 안 됨
DEFAULT 값을 안 주면 자동으로 채울 기본값 주소 미입력 시 ‘미정’
CHECK 값의 범위·조건 제한 학점은 13, 점수는 0100
CONSTRAINT 위 제약에 이름을 붙여 관리 쉽게 CONSTRAINT pk_x PRIMARY KEY(...) 
-- 제약에 이름 붙이기(관리·조회 편하게)
CONSTRAINT 제약조건이름 제약조건(컬럼명)

강사님이 짚은 디테일 두 가지가 중요하다.

💡 UNIQUE는 이메일에 ⭕, 이름엔 ❌. 이메일은 사람마다 달라야 하니 UNIQUE가 맞다. 하지만 이름은 동명이인이 있어 UNIQUE를 걸면 멀쩡한 사람이 가입을 못 한다. 그리고 UNIQUE는 NULL은 중복으로 안 친다 — 이메일을 비워둔 사람은 여러 명 있어도 된다.

💡 DEFAULT vs NOT NULL은 택일. 둘 다 “빈 값 처리” 얘기지만 방향이 다르다. 쇼핑몰 배송지처럼 꼭 있어야 하는 값은 DEFAULT로 대충 채우기보다 NOT NULL로 강제하는 게 낫다. 정답은 비즈니스 로직이 정한다.

⚠️ SQLite 주의: 슬라이드의 SELECT * FROM information_schema...(제약 조회)와 ALTER TABLE ... ADD/DROP CONSTRAINT(제약 추가·삭제)는 MySQL/표준 문법이라 SQLite엔 없다. SQLite에선 제약 조회를 PRAGMA table_info(...)·PRAGMA foreign_key_list(...)로, 제약 변경은 테이블 재생성으로 한다.

06 · 키와 무결성 — PK / FK / 후보·대체·슈퍼키 / 복합키#

테이블에서 행을 구분하고, 테이블끼리 잇는 역할을 하는 게 키(key) 다.

기본키 / 외래키#

  • 기본키(Primary Key, PK): 행을 유일하게 식별하는 기준 속성. 중복 불가 + NULL 불가(= NOT NULL + UNIQUE를 합친 것). 테이블당 보통 1개. 설정은 PRIMARY KEY.
  • 외래키(Foreign Key, FK): 다른 테이블의 기본키를 참조하는 속성. 테이블 간 관계를 만든다. 참조하는 값은 부모 테이블 PK에 실제로 있는 값(또는 NULL)만 가능 → 이게 참조 무결성. 설정은 FOREIGN KEY (컬럼) REFERENCES 부모테이블(부모컬럼).

비유하면, PK는 주민등록번호(나를 유일하게 가리킴), FK는 가족관계증명서에 적힌 부모의 주민번호(존재하는 사람만 적을 수 있음)다.

후보키 · 대체키 · 슈퍼키#

키 정의 유일성 최소성
슈퍼키 유일하게 식별은 되지만 불필요한 속성이 섞임 ⭕ ❌
후보키 기본키가 될 자격이 있는 키 ⭕ ⭕
대체키 후보키 중 기본키로 안 뽑힌 키 ⭕ ⭕
  • 유일성 = 그 값으로 행을 하나로 특정할 수 있음
  • 최소성 = 더 빼면 식별이 안 되는, 꼭 필요한 속성만 남은 상태

복합 기본키(Composite Key)#

칼럼 하나로 식별이 안 될 때 두 개 이상을 묶어 PK로 삼는다. 오늘 실습의 enrollment(student_id, course_id)가 그 예 — “어떤 학생이 어떤 강의를 듣는가"는 학생+강의 한 쌍이 있어야 한 건으로 특정된다.

무결성 제약 — 데이터가 지켜야 할 규칙들#

무결성 규칙
개체 무결성 기본키는 NULL·중복 불가
참조 무결성 외래키는 부모 PK에 있는 값이거나 NULL
도메인 무결성 값은 그 속성의 허용 범위(도메인) 안
NULL 무결성 특정 속성은 NULL 불가
고유 무결성 각 튜플의 값이 서로 다름
키 무결성 테이블엔 최소 한 개의 키가 존재

07 · 데이터 모델링 — 현실을 표로 옮기는 과정#

데이터 모델링은 현실 세계의 데이터를 데이터베이스로 옮기는 설계 작업이다. 세 가지 재료로 구성된다.

  • 개체(Entity): 관리 대상 (예: 학생, 강의)
  • 속성(Attribute): 개체의 특성·정보 (예: 학생의 이름, 학번)
  • 관계(Relationship): 개체 간 연관 (예: 학생이 강의를 수강한다)

과정은 개념적 설계 → 논리적 설계 → 물리적 설계 3단계로 추상에서 구체로 내려간다.

08 · ERD — 테이블 관계를 그림으로 그리는 설계도#

ERD(Entity-Relationship Diagram) 는 테이블들이 서로 어떻게 연결되는지를 그림으로 보여주는 설계도다. 구성요소는 셋이다.

  • 개체(Entity): 박스 하나 = 테이블 하나
  • 속성(Attribute): 박스 안 항목 = 컬럼 (🔑 = PK)
  • 관계(Relationship): 박스를 잇는 선, 선 끝 모양 = 카디널리티(수량)

Peter Chen 표기법#

기호 의미
사각형 개체(Entity)
타원 속성(Attribute)
마름모 관계(Relationship)
밑줄 기본키
이중 타원 다중값 속성

카디널리티는 1(1:1), <(1:N), ><(N:M)로 표기한다. 도구로는 draw.io(app.diagrams.net)가 소개됐다.

IE(까마귀발) 표기법#

실무에서 더 자주 보는 표기다. 선 끝의 새 발(crow’s foot) 모양으로 수량을 나타낸다.

기호 의미
─┼ 하나(one), 1
─○ 영(zero), 0
─< 다수(many), N

이걸 조합해 0..1(없거나 하나), 1..N(하나 이상 필수), 0..N(없거나 여럿)을 표현한다. 예를 들어 한쪽이 ┼, 반대쪽이 <면 일대다(1:N) 관계다.

관계 유형과 N:M 분해 (강사 강조)#

💡 기본은 일대다(1:N)로 생각하라. 일대일(1:1)은 보안·민감정보 분리처럼 매우 예외적인 경우다. 그리고 다대다(N:M)는 그대로 두지 않고, 최종적으로 중간(연결) 테이블로 분해해 1:N 둘로 만든다. 오늘 실습의 enrollment가 바로 그것 — 학생(N)과 강의(M)의 N:M을, 학생–enrollment(1:N)와 강의–enrollment(1:N)로 푼 것이다. (이 “분해"가 정규화의 일부이고, 정규화는 다음 시간 상세 예고.)

💡 선택/필수 관계: ERD Editor에선 관계가 0..N(선택적)인지 1..N(필수 포함)인지도 정한다. 예) 고객–계좌에서 “계좌가 꼭 있어야 하는가"에 따라 갈린다.

ERD Editor 실습 (코드 ↔ ERD 양방향)#

VS Code 확장 ERD Editor를 쓰면 SQL과 그림을 서로 변환할 수 있다.

  1. VS Code에서 ERD Editor 확장 설치
  2. 작업 폴더에 .erd 파일 생성 (예: school_db.erd)
  3. ERD 화면 우클릭 → Database → SQLite → Import → Schema SQL → 우리가 만든 SQL을 불러오면 관계도가 자동 생성
  4. 반대로 Export → .sql 하면 CREATE 문이 생성됨

💡 강사 강조: 코드 → ERD, ERD → 코드 둘 다 되지만, 내보낸 SQL은 반드시 최종 검토·수정 후 적용해야 한다. 자동 생성을 맹신하지 말 것.

마무리#

오늘은 데이터를 꺼내 쓰는 쪽에서 설계하고 만드는 쪽으로 넘어왔다. DB가 필요한 이유(파일처리의 종속성·중복·무결성 한계)에서 출발해, RDB vs NoSQL로 선택지를 보고, CREATE/INSERT/SELECT로 표를 만들었다. DDL/DML/DCL로 SQL의 갈래를 잡고, 자료형을 정한 뒤, 오늘의 핵심인 제약조건(NOT NULL·UNIQUE·DEFAULT·CHECK·CONSTRAINT)과 키·무결성(PK·FK·후보·대체·슈퍼키·복합키)을 다뤘다. 마지막으로 데이터 모델링과 ERD(Peter Chen·까마귀발·ERD Editor)로 설계를 그림으로 옮겼다. 한 문장으로 남기자면 — 제약조건은 잘못된 데이터를 막는 마지막 방어선이고, 키는 행을 식별하고 테이블을 잇는 손잡이다. 그리고 N:M은 중간 테이블로 분해한다는 것, SQLite는 표준/MySQL 문법 일부를 못 쓴다는 것을 기억해두자. 정규화·카디널리티 심화는 다음 시간이다.
