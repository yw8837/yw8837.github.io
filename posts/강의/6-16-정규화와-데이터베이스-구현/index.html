6/16 정규화 & 데이터베이스 구현 — 같은 데이터인데 왜 1NF·2NF·3NF로 쪼개야 하는가

이어드림 6기 정규화 & 데이터베이스 구현 강의 정리. 이상현상(삽입·갱신·삭제 Anomaly), 함수 종속(부분·이행·완전·결정자), 1NF(원자값)·2NF(부분 함수 종속 제거)·3NF(이행 함수 종속 제거)를 학생/수강/학과 예제로 직관적으로 풀고, BCNF·4NF(다치 종속)·5NF(조인 종속)·역정규화와 "3NF면 충분"의 기준선, 공유킥보드 최종 4테이블 ERD를 정리한다. 후반 MySQL DB 구현(윈도우/맥 설치, CREATE/USE DATABASE, DCL GRANT/REVOKE/CREATE USER, 인덱스 CREATE/SHOW/DROP과 사용 전략)을 다루고, 실습 SQLite vs 슬라이드 MySQL 차이(권한·DATABASE·SHOW INDEX 부재)를 라벨로 구분한다.

지난 시간엔 제약조건·키로 테이블 하나를 잘 만드는 법을 배웠다. 오늘은 한 칸 위로 올라간다 — 테이블들을 어떻게 나눠야 데이터가 꼬이지 않는가, 바로 정규화(Normalization) 다. 출발점은 “왜 굳이 쪼개나?“인데, 답은 잘못 설계하면 데이터를 넣고·고치고·지울 때 사고가 난다(이상현상)는 데 있다. 그래서 오늘은 → 이상현상(삽입·갱신·삭제) → 함수 종속(부분·이행) → 1NF → 2NF → 3NF 로 같은 학생·수강 데이터를 단계적으로 쪼개고 → BCNF·4NF·5NF·역정규화 정리 → 공유킥보드 최종 4테이블 ERD 로 마무리한다. 후반부는 MySQL DB 구현(설치·DATABASE 생성·DCL·인덱스)이다. 관통하는 한 문장은 — “정규화는 ERD를 한 번에 그리는 게 아니라, 단계적으로 분해해 나가는 과정이다.”

01 · 왜 정규화인가 — 이상현상(Anomaly) 3종#

먼저 왜 테이블을 쪼개야 하는지부터. 한 테이블에 모든 걸 욱여넣으면(예: 학생·수강·과목·교수·학과를 한 표에) 데이터를 다룰 때 세 가지 사고가 난다. 이걸 이상현상(Anomaly) 이라 부르고, 정규화는 바로 이걸 없애려는 작업이다.

이상 종류 무슨 뜻인가 학생 DB 예시
삽입 이상(Insertion) 넣고 싶은 데이터만 넣고 싶은데, 관련 없는 데이터가 없으면 못 넣음 아직 학생이 한 명도 없는 신설 학과를 등록할 수 없다 (학생 행에 끼워 넣어야 하므로)
갱신 이상(Update) 한 사실이 여러 행에 중복 저장돼 있어, 일부만 고치면 데이터가 어긋남 학과 건물이 바뀌면 그 학과 학생 행을 전부 고쳐야 한다. 일부만 고치면 같은 학과인데 건물이 제각각
삭제 이상(Deletion) 한 행을 지웠더니 원치 않는 정보까지 같이 사라짐 마지막 학생을 지우면 그 학과 정보까지 통째로 소멸

💡 세 이상의 공통 원인은 “중복"이다. 같은 사실(학과 건물, 교수 연구실)이 여러 행에 복제돼 있어서 생긴다. 정규화 = 중복을 줄여 무결성↑·중복↓. 단계는 1NF → 2NF → 3NF → BCNF → 4NF → 5NF.

💡 강사 강조: 정규화는 ERD를 한 번에 그려 최종 형태를 만드는 게 아니라, 지속적으로 변경(단계적 분해)해 나가는 과정이다. 비정규화 한 덩어리에서 시작해 1NF·2NF·3NF로 차근차근 쪼갠다.

02 · 함수 종속 — 부분 종속 / 이행 종속 / 결정자#

정규화의 “쪼개는 기준"을 알려면 먼저 함수 종속(Functional Dependency) 을 알아야 한다.

함수 종속이란, 어떤 속성 X의 값을 알면 다른 속성 Y의 값이 하나로 정해질 때를 말하고 X → Y 로 쓴다(“X가 Y를 결정한다”). 예: 학번 → 학생이름 — 학번 001만 알면 이름 홍길동이 하나로 확정된다. 반대로 학생이름 → 학번은? 동명이인이 있으니 하나로 안 정해진다. 그래서 함수 종속엔 방향이 있다.

정규화에서 중요한 두 가지 “나쁜” 종속이 있다. 둘 다 복합키(여러 컬럼을 묶은 기본키) 상황에서 등장한다. 예제는 기본키 = (학번 + 과목코드) 인 수강 테이블이다.

종류 정의 예시 어느 정규형이 해결?
부분 함수 종속(Partial) 복합키 일부에만 종속 학생이름 → 학번(과목코드는 무관), 과목이름 → 과목코드 2NF
이행 함수 종속(Transitive) 키가 아닌 속성을 거쳐서 간접 종속 (X→Y, Y→Z ⇒ X→Z) 학번 → 학과코드 → 학과이름 (학과코드는 일반 컬럼) 3NF
(참고) 완전 함수 종속 복합키 전체가 있어야 결정 성적 → (학번 + 과목코드) 둘 다 필요 정상

💡 부분 vs 이행, 한 문장 구분. 부분 종속은 “복합키의 일부 조각만으로 값이 정해지는” 문제(→ 2NF가 해결). 이행 종속은 “중간 컬럼을 거쳐 간접적으로 정해지는” 문제(→ 3NF가 해결).

결정자(Determinant) 는 X → Y에서 다른 속성을 결정하는 쪽인 X를 가리킨다. 뒤에 나올 BCNF가 “결정자이면서 후보키가 아닌 것"을 제거하는 정규형이라, 이 용어를 미리 알아두면 좋다.

03 · 1차 정규화(1NF) — 원자값#

1NF의 규칙은 딱 하나 — 모든 칸에 값이 하나만(원자값, atomic) 들어가야 한다. 한 칸에 여러 값을 콤마로 욱여넣으면 안 된다.

비정규화 테이블에는 이런 칸이 있다.

student_id | student_name | course_ids
101        | 김민준        | 'CS301,CS302'   ← 한 칸에 두 과목! (다중값)

course_ids에 'CS301,CS302'처럼 두 값이 들어가면, WHERE course_id = 'CS301' 같은 조회·JOIN·ORDER BY가 정상 동작하지 않는다. 그래서 다중값을 행으로 쪼갠다.

student_id | course_id | student_name | ...
101        | CS301     | 김민준        | ...
101        | CS302     | 김민준        | ...   ← 행 분리 (원자값)
  • 변화: student_course_all(다중값) → student_course_1nf(원자값). 이제 기본키는 복합 PK (student_id, course_id) 다(한 학생의 한 과목이 한 행).
  • 아직 남은 문제: 여전히 단일 테이블이라 김민준·학과·교수 정보가 행마다 중복 저장된다 → 2NF·3NF가 필요하다.

💡 1NF는 “값을 쪼개는” 단계다. 테이블을 나누는 건 아직 시작 안 했다 — 그건 2NF부터.

04 · 2차 정규화(2NF) — 부분 함수 종속 제거#

2NF의 규칙 — 1NF를 만족하면서, 부분 함수 종속을 제거(= 모든 비키 속성이 복합키 전체에 완전 종속)한다. 쉽게 말해 “복합키의 일부 조각에만 매달린 컬럼을 따로 빼낸다.”

위 1NF 테이블의 복합키는 (학번 + 과목코드)였다. 그런데:

  • 학생이름은 학번만 알면 정해진다 → 과목코드는 불필요 → 부분 종속
  • 과목이름·교수는 과목코드만 알면 정해진다 → 학번은 불필요 → 부분 종속
  • 성적만 학번·과목코드 둘 다 필요 → 완전 종속(이건 정상)

그래서 각각이 매달린 키 기준으로 테이블을 3개로 분리한다.

분리된 테이블 무엇을 담나 키
student_2nf 학생 정보(이름, 학과) student_id (PK)
course_2nf 과목·교수 정보 course_id (PK)
enrollment 수강=성적 (연결 테이블) 복합 PK (student_id, course_id) + FK 2개
  • 학생이름은 student_2nf로, 과목이름·교수는 course_2nf로 빠지면서 부분 종속이 사라졌다.
  • 하지만 아직 한 가지 문제가 남는다: student_2nf 안에 학과 정보(dept_code/dept_name/dept_building)가 학생과 같이 들어 있다. 학번 → 학과코드 → 학과건물이라는 이행 종속이 남아 있어서, 학과 건물을 바꾸면 그 학과 학생 행을 전부 고쳐야 하는 갱신 이상이 여전히 발생한다. → 3NF가 필요하다. (코드 노트의 데모가 이 “2NF의 학과 갱신 이상 잔존"을 눈으로 보여준다.)

05 · 3차 정규화(3NF) — 이행 함수 종속 제거#

3NF의 규칙 — 2NF를 만족하면서, 이행 함수 종속을 제거한다. 즉 X → Y → Z처럼 중간 컬럼(Y)을 거쳐 간접 종속되는 관계를 끊고, Y → Z를 독립 테이블로 빼서 FK로 연결한다.

2NF에서 남았던 학번 → 학과코드 → 학과건물을 처리하자. 학과(department) 를 독립 테이블로 분리하면, 학생 테이블은 학과의 ID만 FK로 가리키면 된다. 교수도 마찬가지로 professor로 분리한다. 결과는 5테이블이다.

테이블 역할
department 학과 마스터(학과코드·이름·건물). 학과 정보가 여기 한 곳에만 존재
professor 교수 마스터(이름·연구실), dept_id(FK)
student 학생, dept_id(FK)만 가짐 (학과 정보는 안 가짐)
course 과목, professor_id(FK)만 가짐
enrollment_3nf 수강=성적, 복합 PK + FK 2개
  • 이제 학과 건물을 바꿀 땐 department 한 행만 고치면 끝(UPDATE department ... WHERE dept_code = ?) → 갱신 이상 해소.
  • 학과의 마지막 학생을 지워도 department에 학과가 남으므로 삭제 이상도 없다.
  • 결과: 삽입·갱신·삭제 이상이 모두 사라진다. (데모에서 3NF = 모든 시나리오 “정상”.)

💡 2NF와 3NF의 차이를 가장 직관적으로 보여주는 건 “학과 갱신 이상"이다. 2NF까지는 학과 정보가 학생 테이블에 붙어 있어 갱신 이상이 남고, 3NF에서 학과를 독립 테이블로 빼야 비로소 사라진다.

06 · 정규화 정리 — BCNF / 4NF / 5NF / 역정규화#

3NF 위로도 정규형이 더 있다. 다만 실무에서 거의 안 쓰니 개념만 잡고 넘어간다.

단계 흐름 전체: 비정규화 → 1NF(원자값) → 2NF(부분 종속 제거) → 3NF(이행 종속 제거) → BCNF(결정자≠후보키 제거) → 4NF(다치 종속 제거) → 5NF(조인 종속 제거)

정규형 무엇을 제거하나 한 줄 직관
BCNF 결정자이면서 후보키가 아닌 것 예: “교수가 과목을 결정하지만 교수는 후보키가 아닌” 경우를 분리
4NF 다치 종속(Multivalued Dependency) 한 과목에 교수·교재처럼 서로 독립적인 다중값이 섞여 불필요한 조합 행이 생기는 걸 분리
5NF 조인 종속(Join Dependency) 테이블을 더 잘게 쪼갰다 다시 조인해 복원할 때 가짜(불필요) 행이 생기는 걸 막음

역정규화(Denormalization) — 일부러 되돌리기#

정규화의 반대 방향도 있다. 테이블을 너무 잘게 쪼개면 조회할 때마다 여러 테이블을 JOIN해야 해서 성능이 떨어질 수 있다. 그래서 조회가 아주 잦은 곳에서는 의도적으로 중복을 허용해 테이블을 다시 합치기도 하는데, 이를 역정규화라 한다.

⚠️ 역정규화는 함부로 하지 않는다. 중복이 생기는 만큼 무결성이 깨질 위험이 따라온다 → 반드시 성능 측정·근거가 있어야 한다.

“3NF면 충분한가?” — 실무 기준선#

  • Codd(정규화 창시자): “3NF는 응용 프로그램의 생명주기를 크게 연장한다”(관계를 이해·조작하기 쉬워진다).
  • 역정규화가 정당한 예외:
    • Read-heavy(조회 위주) 시스템 — JOIN 비용을 줄이려 의도적 비정규화
    • OLAP/데이터웨어하우스 — Star Schema·Snowflake Schema 같은 비정규화 구조가 표준
    • NoSQL/Event Sourcing — 문서 DB·불변 로그는 정규화 개념을 다르게 적용
    • 초소형 프로젝트 — 데이터가 적고 정적이면 단순 구조가 유리
  • 결론: 4NF·5NF는 존재하지만 실무는 보통 3NF로 충분(99%의 응용). 3NF는 타협 불가 기준선이고, 거기서 이탈(역정규화)할 땐 성능 측정·아키텍처 근거가 필요하다.

07 · 공유킥보드 최종 DB — 4테이블 ERD#

요구사항 모델링 → 정규화를 거치면, 공유킥보드 서비스의 최종 ERD는 4개 테이블로 정리된다. 정규화의 “도착점"을 보여주는 예시다.

관계: customer 1—N borrow N—1 kickboard N—1 brand (고객 1명이 여러 번 대여 → 한 번의 대여는 한 킥보드 → 킥보드는 한 브랜드 소속)

테이블 키·주요 컬럼
customer (고객) PK customer_number / name·id(UNIQUE)·pw·phone_number·birth_date
borrow (대여) 복합 PK (customer_number, rental_time DATETIME) / lat_location·lon_location·rental_status ENUM('대여','반납') / FK kickboard_id
kickboard (킥보드) PK id / FK brand_number / model_year·price_per_minute·basic_price
brand (브랜드) PK brand_number / name(UNIQUE)·company

⚠️ 자료형은 MySQL 기준 표기다. ERD에 ENUM('대여','반납')·DATETIME·FLOAT가 쓰였는데, ENUM은 MySQL 자료형이라 SQLite엔 없다(SQLite에선 CHECK로 대체). 슬라이드 ERD가 MySQL 기준으로 그려졌다는 뜻이다.

여기서부터(08~11)는 DB 구현 — 모두 ⚠ MySQL 기준 이다. 실습은 SQLite지만, 이 슬라이드들은 MySQL CLI를 전제로 한다.

08 · DB 구현 ① MySQL 설치 (윈도우 / 맥) ⚠ MySQL 기준#

MySQL은 서버형 DBMS다(SQLite처럼 파일 하나가 아니라, 서버를 켜고 접속한다). OS별 설치·실행 방법이다.

윈도우

# 방법 A: 공식 installer — https://dev.mysql.com/downloads/installer/
# 방법 B: 패키지매니저 Chocolatey 사용 (https://chocolatey.org/install)
#   → PowerShell을 "관리자 권한"으로 실행해 Chocolatey 먼저 설치
choco install mysql        # 설치
net start mysql            # 서버 실행
mysql -u root -p           # 접속 (-p: 비밀번호 입력)
quit                       # 접속 종료 (또는 \q)
net stop mysql             # 서버 종료

맥

# Homebrew 설치 — https://brew.sh/index_ko (안내 명령 복사 실행)
brew install mysql         # 설치
mysql.server start         # 서버 실행
mysql -u root              # 접속
quit                       # 접속 종료
mysql.server stop          # 서버 종료

💡 net start mysql(윈도우) / mysql.server start(맥) 처럼 서버를 먼저 켜야 접속이 된다. SQLite엔 이런 “서버 켜기” 단계가 없다(파일을 열면 끝).

09 · DB 구현 ② 데이터베이스 생성 ⚠ MySQL 기준#

MySQL 서버 하나 안에 여러 데이터베이스를 만들 수 있다. USE로 “지금부터 이 DB를 쓰겠다"고 컨텍스트를 지정한 뒤, 그 안에서 테이블을 다룬다.

CREATE DATABASE shared_kickboard;   -- 데이터베이스 생성
SHOW DATABASES;                     -- 데이터베이스 목록 확인
USE shared_kickboard;               -- 사용할 DB 지정 (이 안에서 테이블 조작)
DROP DATABASE shared_kickboard;     -- 데이터베이스 삭제

⚠️ SQLite 주의: SQLite는 파일 1개 = DB 1개라서 CREATE DATABASE·USE 개념 자체가 없다. 새 DB가 필요하면 새 파일을 만들면 된다. 이건 MySQL만의 관리 단위다.

10 · DB 구현 ③ DCL — GRANT / REVOKE ⚠ MySQL 기준#

지난 시간에 SQL을 DDL/DML/DCL 셋으로 나눴는데, 오늘은 그 DCL(Data Control Language, 데이터 제어어) 을 실제로 쓴다. DCL은 DB에 접근하는 권한을 관리하는 명령이다.

명령 하는 일
GRANT 권한 부여
REVOKE 권한 회수
COMMIT 트랜잭션을 영구 반영
ROLLBACK 트랜잭션 작업 취소(이전 상태 복원) 
-- 1) 사용자 생성
CREATE USER 유저이름@localhost IDENTIFIED BY '비밀번호';
-- localhost = 로컬 접속만 허용. 외부 접속까지 허용하려면 % 사용

-- 2) 권한 부여 + 즉시 적용
GRANT ALL PRIVILEGES ON 데이터베이스.테이블 TO 유저이름@localhost;
FLUSH PRIVILEGES;   -- 변경한 권한을 즉시 적용
-- ALL 대신 SELECT / INSERT / DELETE 등 개별 권한도 지정 가능

-- 3) 권한 확인 / 회수
SHOW GRANTS FOR 유저이름@localhost;                       -- 권한 확인
REVOKE ALL ON 데이터베이스.테이블 FROM 유저이름@localhost; -- 권한 회수

💡 권한을 꼭 필요한 만큼만 주는 게 보안의 기본이다. 분석가에겐 보통 SELECT만 주는 식. 그래서 GRANT ALL보다 GRANT SELECT처럼 개별 권한을 명시하는 경우가 많다.

⚠️ SQLite 주의: SQLite는 사용자·권한 개념이 아예 없다. 따라서 CREATE USER·GRANT·REVOKE·SHOW GRANTS·FLUSH PRIVILEGES는 모두 MySQL 전용으로, SQLite에선 쓸 수 없다. (단 트랜잭션 COMMIT/ROLLBACK은 SQLite도 지원한다.)

11 · DB 구현 ④ 인덱스(Index) ⚠ MySQL 기준#

인덱스(Index) 는 테이블의 검색 속도를 높이는 자료구조다. 책 맨 뒤의 색인과 같다 — 책 전체를 처음부터 넘기지 않고, 색인에서 단어 위치를 바로 찾는 것처럼.

인덱스의 장점 / 단점
장점 검색 속도·조회 성능 ↑
단점 추가 저장공간 필요. 삽입/수정/삭제가 잦으면 인덱스도 매번 갱신돼 오히려 느려질 수 있음

인덱스를 거는 게 유리한 경우(전략):

  • 크기가 큰 테이블
  • 삽입/수정/삭제가 적은 테이블
  • WHERE·ORDER BY·JOIN에 자주 쓰는 컬럼
  • 데이터 중복도가 낮은(고유값이 많은) 컬럼 — 예: 이메일, 주민번호류
CREATE INDEX 인덱스명 ON 테이블명(컬럼명);   -- 인덱스 추가
SHOW INDEX FROM 테이블명;                    -- 인덱스 확인
ALTER TABLE 테이블명 DROP INDEX 인덱스명;     -- 인덱스 삭제

💡 모든 컬럼에 인덱스를 거는 건 오히려 독. 인덱스는 “자주 검색하는 조건 컬럼"에 선택적으로 건다. SELECT * FROM처럼 전체를 다 읽는 쿼리엔 인덱스가 도움이 안 된다.

⚠️ SQLite 주의: CREATE INDEX는 SQLite도 동일하지만, SHOW INDEX FROM ...은 미지원(SQLite는 PRAGMA index_list(테이블) 사용), 삭제도 DROP INDEX 인덱스명; 문법이라 MySQL의 ALTER TABLE ... DROP INDEX와 다르다.

마무리#

오늘은 “테이블 하나 잘 만들기"에서 “테이블들을 어떻게 나눌까“로 올라섰다. 핵심은 잘못된 설계가 부르는 이상현상(삽입·갱신·삭제)이고, 그 원인은 중복이다. 이를 없애려고 같은 학생·수강 데이터를 1NF(원자값) → 2NF(부분 종속 제거, 3테이블) → 3NF(이행 종속 제거, 5테이블) 로 단계적으로 쪼갰다. 특히 2NF까지 남는 “학과 갱신 이상"이 3NF에서 사라진다는 게 둘의 차이를 가장 잘 보여준다. 그 위의 BCNF·4NF·5NF는 이론적 완전성이고, 성능을 위해 일부러 되돌리는 역정규화도 있지만 — 실무는 보통 3NF면 충분하다(타협 불가 기준선). 마지막으로 정규화의 도착점인 공유킥보드 4테이블 ERD를 봤고, 후반부는 MySQL DB 구현(설치·DATABASE 생성·DCL GRANT/REVOKE·인덱스)을 정리했다. 한 줄로 남기면 — 정규화는 한 번에 그리는 그림이 아니라 단계적으로 분해해 나가는 과정이고, 3NF가 그 실무 기준선이다. 실습은 SQLite, DB 구현 슬라이드는 MySQL 기준이라는 차이도 꼭 기억하자.
