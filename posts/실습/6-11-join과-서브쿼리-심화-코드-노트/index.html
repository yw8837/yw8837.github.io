01 · SELF JOIN ① 직원-관리자 (계층형) — chinook#

① 한 줄 설명 — employees 한 테이블을 별칭 2개(직원 e / 관리자 m)로 분리해, 각 직원과 그 관리자를 한 줄에 나란히 본다.

② 코드 (출처: Day04_1_Join_lecture.sql 문제24 — ✅ 실제 답지, 노션 강조)

SELECT e.FirstName || ' ' || e.LastName  AS EmployeeName,
       e.Title                           AS EmployeeTitle,
       m.FirstName || ' ' || m.LastName  AS ManagerName,
       m.Title                           AS ManagerTitle
FROM employees e
LEFT JOIN employees m ON e.ReportsTo = m.EmployeeId
ORDER BY e.EmployeeId;

③ 출력 결과 — 각 직원 옆에 그 직원의 관리자 이름·직책이 붙는다. 최상위(사장, ReportsTo가 NULL)는 관리자 칸이 NULL로 나온다.

④ 한 줄씩 뜯어보기

  • FROM employees e ... JOIN employees m : 같은 테이블을 두 번 불러 별칭 e(직원)·m(관리자)로 구분 → SELF JOIN의 본질.
  • ON e.ReportsTo = m.EmployeeId : “직원의 관리자ID(ReportsTo) = 관리자의 사번(EmployeeId)“로 자기 자신과 연결.
  • LEFT JOIN인 이유 : 관리자가 없는 최상위 직원도 결과에서 빠지지 않게 보존(INNER면 사장이 사라진다).

⑤ 💡 팁 — SELF JOIN은 별칭이 곧 전부다. e/m 같은 의미 있는 별칭을 쓰면 “누가 직원이고 누가 관리자인지"가 쿼리만 봐도 읽힌다.

02 · SELF JOIN ② 차상위 관리자 (Grand Manager) — chinook#

① 한 줄 설명 — 같은 테이블을 세 번(직원·관리자·관리자의 관리자) 이어 붙여 2단계 위 상사까지 본다.

② 코드 (출처: Day04_1_Join_lecture.sql 문제25 — ✅ 실제 답지)

SELECT e.FirstName || ' ' || e.LastName  AS Employee,
       m.FirstName || ' ' || m.LastName  AS DirectManager,
       g.FirstName || ' ' || g.LastName  AS GrandManager
FROM employees e
LEFT JOIN employees m ON e.ReportsTo  = m.EmployeeId
LEFT JOIN employees g ON m.ReportsTo  = g.EmployeeId
ORDER BY e.EmployeeId;

③ 출력 결과 — 직원 / 직속 관리자 / 차상위 관리자(관리자의 관리자) 3컬럼. 위로 갈수록 NULL이 생긴다(사장은 직속·차상위 모두 NULL).

④ 한 줄씩 뜯어보기

  • 첫 LEFT JOIN(m) : 01과 동일, 직원→직속 관리자.
  • 두 번째 LEFT JOIN(g) : m.ReportsTo = g.EmployeeId → 관리자(m)의 관리자(g) 를 한 단계 더 연결.
  • 계층을 한 단계 더 보고 싶으면 같은 패턴으로 JOIN을 또 잇는다(고정 깊이일 때).

⑤ 💡 팁 — JOIN을 반복해 계층을 펼치는 방식은 깊이가 정해져 있을 때(예: 항상 3단계) 간단하다. 깊이를 모르거나 무한 계층이면 어제(6/10) 배운 재귀 CTE(WITH RECURSIVE) 가 더 알맞다.

03 · SELF JOIN ③ 같은 그룹 쌍 비교 — chinook#

① 한 줄 설명 — 자기참조 FK가 없어도, 공통 그룹키(같은 국가/같은 앨범)로 같은 테이블 행끼리 쌍을 만들어 비교한다.

② 코드 (출처: Day04_1_Join_lecture.sql 문제26·27 — ✅ 실제 답지, 문제27 노션 강조)

-- (a) 동일 국가 고객 쌍 (중복 쌍 제거)
SELECT c1.FirstName || ' ' || c1.LastName AS CustomerA,
       c2.FirstName || ' ' || c2.LastName AS CustomerB,
       c1.Country
FROM customers c1
JOIN customers c2
  ON c1.Country    = c2.Country         -- 같은 국가끼리
 AND c1.CustomerId < c2.CustomerId       -- (A,B)만, (B,A)·(A,A) 제거
ORDER BY c1.Country, CustomerA
LIMIT 20;

-- (b) 같은 앨범 안에서 재생시간 차이가 60,000ms(60초) 이내인 트랙 쌍
SELECT t1.Name AS TrackA, t2.Name AS TrackB,
       t1.Milliseconds AS MsA, t2.Milliseconds AS MsB,
       ABS(t1.Milliseconds - t2.Milliseconds) AS MsDiff
FROM tracks t1
JOIN tracks t2
  ON t1.AlbumId =  t2.AlbumId            -- 같은 앨범
 AND t1.TrackId <  t2.TrackId            -- 쌍 중복 제거
 AND ABS(t1.Milliseconds - t2.Milliseconds) <= 60000
ORDER BY MsDiff
LIMIT 15;

③ 출력 결과 — (a) 같은 나라에 사는 고객 두 명씩 짝지은 목록. (b) 같은 앨범 안에서 재생시간이 비슷한(60초 이내) 트랙 쌍이 차이 작은 순으로.

④ 한 줄씩 뜯어보기

  • c1.Country = c2.Country : 조인 키가 자기참조 FK가 아니라 공통 그룹키(같은 국가). 이래도 SELF JOIN이다.
  • c1.CustomerId < c2.CustomerId : 부등호로 (A,B)만 남기고 (B,A) 중복·(A,A) 자기 자신을 제거하는 핵심 트릭.
  • ABS(t1.Ms - t2.Ms) <= 60000 : 재생시간 차의 절댓값으로 “비슷한 길이” 필터(60,000ms = 60초).

⑤ 💡 팁 — 라이브 Q&A 핵심 — “ERD에 자기참조가 없는 테이블도 SELF JOIN이 되나?” → 된다. 같은 그룹(앨범·국가) 안에서 행끼리 비교하면 된다. 쌍 비교에서 부등호(<) 조건은 거의 필수다(안 걸면 중복·자기쌍이 쏟아진다).

04 · LEFT JOIN + IS NULL — 짝 없는 행 찾기 — chinook#

① 한 줄 설명 — “한쪽엔 있는데 다른 쪽엔 짝이 없는” 행을 찾는 정석 패턴. 앨범이 하나도 없는 아티스트를 뽑는다.

② 코드 (출처: Day04_1_Join_lecture.sql 문제17 — ✅ 실제 답지)

SELECT ar.Name AS ArtistName
FROM artists ar
LEFT JOIN albums al ON ar.ArtistId = al.ArtistId
WHERE al.AlbumId IS NULL
ORDER BY ar.Name;

③ 출력 결과 — 등록된 앨범이 하나도 없는 아티스트 이름 목록(이름순).

④ 한 줄씩 뜯어보기

  • LEFT JOIN albums : 아티스트는 전부 보존하고, 앨범이 없으면 album 컬럼이 NULL로 채워진다.
  • WHERE al.AlbumId IS NULL : 그 NULL인 행만 남기면 = 앨범 짝이 없는 아티스트.

⑤ 💡 팁 — LEFT JOIN ... WHERE 오른쪽키 IS NULL은 “주문 없는 고객”, “결제 안 한 회원"처럼 "~가 없는 대상” 찾기의 만능 패턴이다. 조건을 ON이 아니라 WHERE에 둬야 NULL 행이 필터링된다(강의 04 ON vs WHERE 참고).

05 · FULL OUTER JOIN — UNION 대체 — chinook#

① 한 줄 설명 — FULL OUTER JOIN을 LEFT ∪ RIGHT의 UNION으로 구현(구버전 SQLite·MySQL 호환).

② 코드 (출처: Day04_1_Join_lecture.sql 문제23 — ✅ 실제 답지)

SELECT ar.Name AS ArtistName, al.Title AS AlbumTitle
FROM artists ar LEFT JOIN albums al ON ar.ArtistId = al.ArtistId
UNION
SELECT ar.Name AS ArtistName, al.Title AS AlbumTitle
FROM artists ar RIGHT JOIN albums al ON ar.ArtistId = al.ArtistId
ORDER BY ArtistName NULLS LAST;

③ 출력 결과 — 아티스트-앨범 전체 짝. 앨범 없는 아티스트, 아티스트 없는 앨범 양쪽 모두 NULL을 채워 포함된다.

④ 한 줄씩 뜯어보기

  • 위 SELECT(LEFT) : 아티스트 전부 보존. 아래 SELECT(RIGHT) : 앨범 전부 보존.
  • UNION : 둘을 합치며 중복 제거 → 양쪽 다 보존 = FULL OUTER 효과.
  • NULLS LAST : NULL 값을 정렬 맨 뒤로(가독성).

⑤ 💡 팁 — FULL OUTER를 지원하는 최신 SQLite(3.39+)·Oracle이면 FULL OUTER JOIN을 바로 써도 된다. MySQL은 FULL OUTER가 없어 이 UNION 패턴이 사실상 표준 우회법이다(어제 배운 UNION의 실전 활용).

06 · 서브쿼리 ① 연관 vs 비연관 — chinook#

① 한 줄 설명 — 서브쿼리가 메인쿼리 컬럼을 참조하는지로 갈리는 두 동작 방식을 나란히 비교한다.

② 코드 (출처: Day04_2_subquery_lecture.sql 문제2·6 — ✅ 실제 답지, 문제6 노션 강조)

-- (a) 비연관: 전체 평균 단가보다 비싼 트랙 (서브쿼리 한 번만 실행)
SELECT Name, UnitPrice
FROM tracks
WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM tracks)
ORDER BY UnitPrice DESC;

-- (b) 연관: 자기가 속한 '앨범 평균 재생시간'보다 긴 트랙
SELECT t.Name, t.Milliseconds, t.AlbumId
FROM tracks t
WHERE t.Milliseconds > (
    SELECT AVG(t2.Milliseconds)
    FROM tracks t2
    WHERE t2.AlbumId = t.AlbumId       -- 메인쿼리 t.AlbumId 참조 ← 연관
)
ORDER BY t.AlbumId, t.Milliseconds DESC
LIMIT 20;

③ 출력 결과 — (a) 전체 평균 단가 초과 트랙(단가 내림차순). (b) 각자 자기 앨범의 평균 길이보다 긴 트랙(앨범별 기준이 다름).

④ 한 줄씩 뜯어보기

  • (a) 서브쿼리 SELECT AVG(UnitPrice) FROM tracks는 메인쿼리와 무관 → 한 번 계산해 모든 행에 같은 기준 적용 = 비연관.
  • (b) 서브쿼리 안 WHERE t2.AlbumId = t.AlbumId에 메인쿼리 별칭 t가 들어옴 → 행마다 앨범이 달라 다시 계산 = 연관.

⑤ 💡 팁 — 구분법: 서브쿼리만 따로 떼어 실행할 수 있으면 비연관, 메인쿼리 별칭이 있어 단독 실행이 안 되면 연관이다. 연관 서브쿼리는 행마다 재실행되니 데이터가 크면 느릴 수 있다는 점도 기억하자.

07 · 서브쿼리 ② EXISTS vs IN (같은 결과) — chinook#

① 한 줄 설명 — “판매된 적 있는 트랙"을 연관 EXISTS와 비연관 IN 두 방식으로 똑같이 구한다.

② 코드 (출처: Day04_2_subquery_lecture.sql 문제7·8 — ✅ 실제 답지)

-- 7. 연관 EXISTS
SELECT t.Name FROM tracks t
WHERE EXISTS (SELECT 1 FROM invoice_items ii WHERE ii.TrackId = t.TrackId)
ORDER BY t.Name LIMIT 10;

-- 8. 비연관 IN (동일 결과)
SELECT t.Name FROM tracks t
WHERE t.TrackId IN (SELECT ii.TrackId FROM invoice_items ii)
ORDER BY t.Name LIMIT 10;

③ 출력 결과 — 두 쿼리 모두 “한 번이라도 판매된(invoice_items에 등장한) 트랙” 이름을 동일하게 반환.

④ 한 줄씩 뜯어보기

  • EXISTS (SELECT 1 ...) : 결과의 존재 여부만 본다. SELECT 1은 “뭐든 한 줄이라도 있나"만 확인하니 값은 의미 없다. ii.TrackId = t.TrackId로 메인 트랙과 연관.
  • IN (SELECT ii.TrackId ...) : 판매된 TrackId 목록을 먼저 만들고 거기 속하는지 비교(비연관).

⑤ 💡 팁 — 결과는 같지만 보통 존재 여부만 보면 EXISTS, 값 목록과 대조하면 IN이 자연스럽다. 반대 의미(“판매 안 된 트랙”)는 NOT EXISTS / NOT IN인데, NOT IN은 목록에 NULL이 섞이면 결과가 비는 함정이 있어 NOT EXISTS가 더 안전하다.

08 · 서브쿼리 ③ ALL/ANY → MAX/MIN 대체 (SQLite) — chinook#

① 한 줄 설명 — SQLite엔 ALL/ANY가 없어 MAX/MIN 스칼라 서브쿼리로 같은 의미를 만든다.

② 코드 (출처: Day04_2_subquery_lecture.sql 문제17·18 — ✅ 실제 답지, SQLite 대체 패턴)

-- 17. Rock '모든' 트랙보다 긴 트랙 → >= ALL 대체: MAX
SELECT Name, Milliseconds FROM tracks
WHERE Milliseconds > (SELECT MAX(t.Milliseconds) FROM tracks t
                      INNER JOIN genres g ON t.GenreId = g.GenreId
                      WHERE g.Name = 'Rock')
ORDER BY Milliseconds DESC LIMIT 10;

-- 18. Classical '어떤' 트랙보다 긴 트랙 → > ANY 대체: MIN
SELECT Name, Milliseconds FROM tracks
WHERE Milliseconds > (SELECT MIN(t.Milliseconds) FROM tracks t
                      INNER JOIN genres g ON t.GenreId = g.GenreId
                      WHERE g.Name = 'Classical')
ORDER BY Milliseconds LIMIT 10;

③ 출력 결과 — 17: Rock 최장 트랙보다도 긴 트랙. 18: Classical 최단 트랙보다 긴 트랙.

④ 한 줄씩 뜯어보기

  • 17 > MAX(...) : “모든 Rock 트랙보다 길다” = “Rock 중 가장 긴 것보다 길다” → 표준 > ALL과 동치.
  • 18 > MIN(...) : “어떤 Classical 트랙보다라도 길다” = “Classical 중 가장 짧은 것보다 길다” → 표준 > ANY와 동치.

⑤ 💡 팁 — 외우는 법: ALL은 가장 빡센 조건이라 MAX(전부보다 크려면 최댓값보다 커야), ANY는 가장 느슨해서 MIN(하나만 넘으면 되니 최솟값만 넘으면). 슬라이드(표준)는 ALL/ANY로 쓰지만 SQLite 실습은 이 대체형이다.

09 · 서브쿼리 ④ 다중컬럼 — chinook#

① 한 줄 설명 — (컬럼A, 컬럼B)를 한 쌍으로 묶어 서브쿼리 결과와 동시에 비교한다. 각 앨범의 최장 트랙을 뽑는다.

② 코드 (출처: Day04_2_subquery_lecture.sql 문제19 — ✅ 실제 답지)

SELECT Name, AlbumId, Milliseconds
FROM tracks
WHERE (AlbumId, Milliseconds) IN (
    SELECT AlbumId, MAX(Milliseconds) FROM tracks GROUP BY AlbumId
)
ORDER BY AlbumId LIMIT 15;

③ 출력 결과 — 앨범마다 재생시간이 가장 긴 트랙 한 곡(앨범ID순).

④ 한 줄씩 뜯어보기

  • 서브쿼리 SELECT AlbumId, MAX(Milliseconds) ... GROUP BY AlbumId : 앨범별 (앨범ID, 최장시간) 쌍 목록.
  • (AlbumId, Milliseconds) IN (...) : 두 컬럼을 묶어서 그 쌍과 정확히 일치하는 트랙만 = 각 앨범의 최장 트랙.

⑤ 💡 팁 — “그룹별 최댓값을 가진 원본 행"을 뽑는 고전 문제다. 다중컬럼 IN은 라이브에서 새로 강조한 패턴. (단순히 MAX(Milliseconds)만 SELECT하면 곡 이름은 못 가져온다 — 그래서 쌍으로 되짚어 매칭한다.)

10 · 서브쿼리 ⑤ 스칼라 — DUAL 대체 (비율 계산) — chinook#

① 한 줄 설명 — 값 하나만 돌려주는 스칼라 서브쿼리 두 개를 나눠 Rock 장르 비율을 구한다. Oracle의 FROM DUAL 없이.

② 코드 (출처: Day04_2_subquery_lecture.sql 문제25 — ✅ 실제 답지)

SELECT ROUND(
  CAST((SELECT COUNT(*) FROM tracks t INNER JOIN genres g ON t.GenreId=g.GenreId WHERE g.Name='Rock') AS REAL)
  / CAST((SELECT COUNT(*) FROM tracks) AS REAL), 4
) AS RockRatio;

③ 출력 결과 — Rock 트랙 수 ÷ 전체 트랙 수를 소수점 4자리로 반올림한 비율 한 값.

④ 한 줄씩 뜯어보기

  • 두 (SELECT COUNT(*) ...) : 각각 1행 1값 → 스칼라 서브쿼리라 일반 숫자처럼 나눗셈에 들어간다.
  • CAST(... AS REAL) : 정수끼리 나누면 0이 되니 실수로 변환해 소수 비율을 얻는다.
  • FROM 절 없음 : SQLite는 DUAL이 없어 SELECT만 단독으로 쓴다(Oracle은 ... FROM DUAL).

⑤ 💡 팁 — “전체 중 일부 비율"을 한 줄로 뽑는 패턴. 정수 나눗셈 함정(1/2 = 0)을 피하려 CAST ... AS REAL은 거의 항상 필요하다.

11 · VIEW — DROP 후 CREATE / 뷰 위에 뷰 — chinook#

① 한 줄 설명 — 복잡한 4중 조인을 뷰로 저장해 두고 짧게 조회. SQLite는 OR REPLACE가 없어 DROP 후 CREATE.

② 코드 (출처: Day04_2_subquery_lecture.sql 문제27·30 — ✅ 실제 답지)

-- (a) 트랙 상세 뷰 (트랙+앨범+아티스트+장르)
DROP VIEW IF EXISTS view_track_full;
CREATE VIEW view_track_full AS
SELECT t.TrackId, t.Name AS TrackName, t.Milliseconds, t.UnitPrice,
       al.Title AS AlbumTitle, ar.Name AS ArtistName, g.Name AS GenreName
FROM tracks t
INNER JOIN albums  al ON t.AlbumId   = al.AlbumId
INNER JOIN artists ar ON al.ArtistId = ar.ArtistId
INNER JOIN genres  g  ON t.GenreId   = g.GenreId;

SELECT * FROM view_track_full ORDER BY ArtistName, AlbumTitle LIMIT 10;

-- (b) 뷰 위에 뷰: 국가별 고객 수 (view_customer_public 뷰를 다시 집계)
DROP VIEW IF EXISTS view_customer_by_country;
CREATE VIEW view_customer_by_country AS
SELECT Country, COUNT(*) AS CustomerCount
FROM view_customer_public          -- 앞서 만든 뷰를 원본처럼 사용
GROUP BY Country;

SELECT * FROM view_customer_by_country ORDER BY CustomerCount DESC;

③ 출력 결과 — (a) 트랙별로 앨범·아티스트·장르가 한 줄에 합쳐진 결과(이후 SELECT * FROM view_track_full만으로 재사용). (b) 국가별 고객 수가 많은 순으로.

④ 한 줄씩 뜯어보기

  • DROP VIEW IF EXISTS ... : SQLite는 CREATE OR REPLACE VIEW가 없어 먼저 지우고 새로 만든다.
  • (a) CREATE VIEW ... AS SELECT (4중 조인) : 자주 쓰는 복잡한 조인을 한 번 정의 → 다음부턴 테이블처럼 조회.
  • (b) FROM view_customer_public : 뷰를 또 다른 뷰의 재료로 사용(뷰의 중첩).

⑤ 💡 팁 — 뷰는 “복잡한 쿼리 즐겨찾기"다. 단, 데이터를 따로 저장하진 않아 조회마다 원본 쿼리가 다시 돈다. (b)처럼 뷰 위에 뷰를 쌓으면 단계적으로 추상화할 수 있지만, 너무 깊게 쌓으면 성능·디버깅이 어려워진다.

12 · 퀴즈 5문제 — classicmodels.db#

📝 1~3교시 퀴즈(약 30분, 5문제). 학습범위 = JOIN(특히 LEFT JOIN)·교집합(INTERSECT)·서브쿼리(스칼라 포함)·UNION. 5번이 최고난도(강사님: 정답보다 시도·접근 과정 중시). 아래는 노션 실제 답지(Day03_quiz.sql)다.

① 한 줄 설명 — 집계+HAVING, WHERE 서브쿼리, LEFT JOIN, INTERSECT, 복합(서브쿼리+UNION)을 한 문제씩.

② 코드 (출처: 노션 Day03_quiz.sql Q1~Q5 — ✅ 실제 답지)

-- Q1. 제품라인별 제품 수 10개 이상 (집계 + HAVING)
SELECT productLine, COUNT(*) AS 제품수
FROM products
GROUP BY productLine
HAVING 제품수 >= 10
ORDER BY 제품수 DESC;

-- Q2. 평균 MSRP보다 비싼 제품 (WHERE 서브쿼리)
SELECT productCode, productName, MSRP
FROM products
WHERE MSRP > (SELECT AVG(MSRP) FROM products)
ORDER BY MSRP DESC;

-- Q3. 주문 내역 없는 고객 (LEFT JOIN + IS NULL)
SELECT c.customerNumber, c.customerName
FROM customers c
LEFT JOIN orders o ON c.customerNumber = o.customerNumber
WHERE o.orderNumber IS NULL
ORDER BY c.customerNumber;

-- Q4. 2003·2004 모두 주문한 고객 (INTERSECT + JOIN)
SELECT c.customerNumber, c.customerName, c.country, c.city
FROM customers c
JOIN (
    SELECT customerNumber FROM orders WHERE strftime('%Y', orderDate) = '2003'
    INTERSECT
    SELECT customerNumber FROM orders WHERE strftime('%Y', orderDate) = '2004'
) o ON c.customerNumber = o.customerNumber
ORDER BY c.customerNumber;

-- Q5. 2004년 주문 고객(미국/프랑스) + 주문수 (복합: 서브쿼리 + UNION) — 최고난도
SELECT customerNumber, customerName, country, city, orderCount
FROM (
    SELECT c.customerNumber, c.customerName, c.country, c.city,
           (SELECT COUNT(*) FROM orders o
            WHERE o.customerNumber = c.customerNumber
            AND strftime('%Y', o.orderDate) = '2004') AS orderCount
    FROM customers c
    JOIN orders o ON c.customerNumber = o.customerNumber
    WHERE c.country = 'USA' AND strftime('%Y', o.orderDate) = '2004'
    GROUP BY c.customerNumber
    UNION
    SELECT c.customerNumber, c.customerName, c.country, c.city,
           (SELECT COUNT(*) FROM orders o
            WHERE o.customerNumber = c.customerNumber
            AND strftime('%Y', o.orderDate) = '2004') AS orderCount
    FROM customers c
    JOIN orders o ON c.customerNumber = o.customerNumber
    WHERE c.country = 'France' AND strftime('%Y', o.orderDate) = '2004'
    GROUP BY c.customerNumber
)
ORDER BY country, customerNumber;

③ 출력 결과 — Q1: 제품 10개↑ 제품라인. Q2: 평균 MSRP 초과 제품. Q3: 주문 한 번도 없는 고객. Q4: 2003·2004 둘 다 주문한 고객. Q5: 2004년에 주문한 미국·프랑스 고객과 각자의 2004년 주문 건수.

④ 한 줄씩 뜯어보기

  • Q1 HAVING 제품수 >= 10 : GROUP BY로 묶은 그룹에 대한 조건은 WHERE가 아니라 HAVING.
  • Q3 : 04의 LEFT JOIN ... IS NULL 패턴 그대로(주문 없는 고객 = orders 짝 NULL).
  • Q4 : 연도별 고객ID 집합을 INTERSECT(교집합)로 구하고, 인라인 뷰로 감싸 customers와 JOIN해 이름까지(어제 04 패턴).
  • Q5 : 나라별 결과(USA/France)를 UNION으로 합치고, 각 행에 스칼라 서브쿼리로 2004년 주문수를 붙인 복합 쿼리.

⑤ 💡 팁 — Q5는 오늘 배운 거의 모든 걸(JOIN·서브쿼리·스칼라·UNION) 한 번에 쓴다. 이런 문제는 조각으로 쪼개 각각 실행해 검증한 뒤 합치는 게 정답률을 높인다. 강사님도 5번은 완답보다 접근을 봤다.

13-1 · 연결·조회 헬퍼 + 국가별 고객 수 (classicmodels)#

① 한 줄 설명 — sqlite3로 DB에 연결해 쿼리를 실행하는 재사용 함수, 그리고 GROUP BY 집계.

② 코드 (출처: ipynb cell 290fc2fb, 7f911e6a — ✅ 원본)

import sqlite3   # 보완: 셀 실행 순서상 상단에서 import 되어 있어야 함

def run_query(db_path, sql, params=()):
    """SQLite 쿼리 실행 후 (컬럼명 리스트, 행 리스트) 반환"""
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row          # dict처럼 컬럼명으로 접근 가능
    cur = conn.cursor()
    cur.execute(sql, params)
    rows = cur.fetchall()
    columns = [desc[0] for desc in cur.description] if cur.description else []
    conn.close()
    return columns, rows

sql_customers = """
SELECT country, COUNT(*) AS customer_count
FROM customers
GROUP BY country
ORDER BY customer_count DESC
LIMIT 8
"""

③ 출력 결과 — 테이블 목록: ['customers','employees','offices','orderdetails','orders','payments','productlines','products']. 국가별: USA 36 / Germany 13 / France 12 / Spain 7 / UK 5 / Australia 5 / New Zealand 4 / Italy 4.

④ 한 줄씩 뜯어보기

  • sqlite3.connect(db_path) : DB 파일 하나에 연결(MySQL과 달리 호스트·계정 불필요).
  • conn.row_factory = sqlite3.Row : 결과 행을 row['country']처럼 컬럼명으로 읽게 해준다.
  • cur.fetchall() : 실행 결과 행을 한꺼번에 가져온다 → 이후 Python에서 가공.
  • conn.close() : 반드시 닫는다(안 닫으면 파일 잠김 에러 위험).

⑤ 💡 팁 — 한 번 만든 run_query를 계속 재사용하면 쿼리만 갈아끼우며 분석할 수 있다. SQL은 “데이터 뽑기”, Python은 “가공·시각화” — 역할을 나눠 생각하면 흐름이 잡힌다.

13-4 · Python에서 JOIN·서브쿼리 (day04_shop)#

# (a) 4중 JOIN: 고객·주문·주문상세·상품
sql_join = """
SELECT c.customer_name, o.order_id, p.product_name, oi.quantity, p.price,

INNER JOIN orders o       ON c.customer_id = o.customer_id

INNER JOIN products p     ON oi.product_id = p.product_id

sql_sub_in = """

    )
)
ORDER BY o.order_id
"""

③ 출력 결과 — (a) 김민수 1001 아메리카노 ×2=10,890 / 초코칩쿠키 ×1=2,500 / 이영희 1002 녹차 ×3=14,520 / 김민수 1003 물티슈·세제·아메리카노. (b) 세제 8900 / 아메리카노 5445 / 녹차 4840. (c) 주문 1001·1002·1003 모두 음료 포함.

④ 한 줄씩 뜯어보기

  • (a) INNER JOIN 3번 : 고객→주문→주문상세→상품을 차례로 이어 “누가 무엇을 얼마치 샀나"를 한 줄로.
  • (b) WHERE price > (SELECT AVG(price) ...) : 비연관 서브쿼리(전체 평균 한 번 계산).
  • (c) 중첩 IN : 안쪽(음료 product_id) → 그걸 포함한 order_id → 그 주문의 고객. 서브쿼리 2겹.

⑤ 💡 팁 — chinook/classicmodels에서 배운 JOIN·서브쿼리가 내가 만든 작은 DB에서도 똑같이 동작한다 — DB만 바뀌었지 SQL 문법은 그대로다. 중첩 서브쿼리는 안쪽부터 차례로 읽으면 흐름이 보인다.

마무리#

오늘 실습은 JOIN의 여러 얼굴(SELF JOIN 3종·LEFT JOIN으로 짝 없는 행 찾기·FULL OUTER의 UNION 대체)과 서브쿼리의 두 축(연관/비연관 × 단일행/다중행/스칼라), 그리고 VIEW·Python sqlite3 연동까지 손으로 돌려봤다. 같은 개념이 chinook·classicmodels·내가 만든 day04_shop 어디서나 똑같이 동작한다는 것, 그리고 슬라이드의 표준/Oracle 문법(ALL/ANY·DUAL·CREATE OR REPLACE VIEW)이 SQLite에선 MAX/MIN·FROM 생략·DROP+CREATE로 바뀐다는 것이 핵심이었다. 복잡한 퀴즈 Q5처럼 한 쿼리에 여러 개념이 모일 땐 여전히 “분할 → 각각 실행 → 합치기”.
