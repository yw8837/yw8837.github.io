00 · 실습 준비 — DB 파일 + 외래키 켜기#

① 새 DB 파일을 만들고, SQLite에서 꺼져 있는 외래키를 켜는 준비 단계다.

-- ✅ 실제 답지 (Day06_lecture.sql 헤더)
-- DB명: school_db (school_db.db 파일 새로 생성 후 연결)
PRAGMA foreign_keys = ON; -- 외래키 활성화 (반드시 최상단에 선언)

③ 출력: 별도 결과는 없다. 테이블 생성은 조회가 아니라 만드는 작업이라 데이터가 안 보이는 게 정상이다. 생성 여부는 테이블 목록 새로고침으로 확인한다.

④ 한 줄씩:

  • PRAGMA foreign_keys = ON; — SQLite는 FK가 기본 OFF라, 이 한 줄을 빼면 FK 위반을 막지 않고 그냥 통과시킨다. 그러면 제약 실습이 무의미해진다.

💡 연결 대상이 class.db가 아니라 school_db.db인지 먼저 확인하자(강사가 라이브에서 짚은 실수 포인트). 그리고 PRAGMA는 커넥션마다 다시 켜야 한다.

01 · school_db 5테이블 CREATE ✅#

① 학과·교수·학생·강의·수강 5개 테이블을 제약조건까지 넣어 만든다. 설계 포인트: department가 부모, professor/student/course가 dept_id·prof_id로 참조하고, enrollment는 학생–강의를 잇는 연결 테이블(복합 PK + FK 2개) 이다.

[1] department (학과) — PK + NOT NULL + DEFAULT

-- ✅ 실제 답지
CREATE TABLE department (
    dept_id     VARCHAR(10) PRIMARY KEY,
    dept_name   VARCHAR(50) NOT NULL,
    location    VARCHAR(50) DEFAULT '미정'
);

④ dept_id가 기본키(유일·NOT NULL). dept_name은 필수. location은 안 주면 '미정'이 자동으로 들어간다.

[2] professor (교수) — PK + NOT NULL + UNIQUE + CHECK + FK

-- ✅ 실제 답지
CREATE TABLE professor (
    prof_id     VARCHAR(10) PRIMARY KEY,
    name        VARCHAR(20) NOT NULL,
    email       VARCHAR(50) NOT NULL UNIQUE,
    dept_id     VARCHAR(10),
    hire_year   INT CHECK (hire_year >= 1980),
    FOREIGN KEY (dept_id) REFERENCES department(dept_id)
);

④ email은 필수이면서 중복 불가(NOT NULL UNIQUE). hire_year는 1980년 이상만 허용(CHECK). dept_id는 department의 PK를 참조(FOREIGN KEY).

[3] student (학생) — UNIQUE(email) + 복수 CHECK + FK

-- ✅ 실제 답지
CREATE TABLE student (
    student_id   VARCHAR(10) PRIMARY KEY,
    name         VARCHAR(20) NOT NULL,
    email        VARCHAR(50) UNIQUE,
    birth_year   INT CHECK (birth_year >= 1990 AND birth_year <= 2010),
    dept_id      VARCHAR(10),
    grade        INT CHECK (grade >= 1 AND grade <= 4),
    tuition_paid VARCHAR(1)  DEFAULT 'N',
    FOREIGN KEY (dept_id) REFERENCES department(dept_id)
);

④ email은 UNIQUE지만 NOT NULL이 아니다 → 비워둘 수 있고, 빈(NULL) 이메일은 여러 명 있어도 된다(아래 03에서 실증). birth_year·grade는 범위 CHECK. tuition_paid는 기본값 'N'(미납).

[4] course (강의) — NOT NULL + CHECK(학점 1~3) + DEFAULT + FK

-- ✅ 실제 답지
CREATE TABLE course (
    course_id    VARCHAR(10)  PRIMARY KEY,
    title        VARCHAR(100) NOT NULL,
    credit       INT          NOT NULL CHECK (credit >= 1 AND credit <= 3),
    prof_id      VARCHAR(10),
    max_students INT          DEFAULT 30,
    FOREIGN KEY (prof_id) REFERENCES professor(prof_id)
);

④ credit(학점)은 필수이며 1~3 범위. max_students는 안 주면 30. prof_id는 professor 참조.

[5] enrollment (수강, N:M 중간 테이블) — 명명된 복합 PK + FK 2개 + CHECK

-- ✅ 실제 답지
CREATE TABLE enrollment (
    student_id  VARCHAR(10),
    course_id   VARCHAR(10),
    enroll_date DATE NOT NULL,
    score       INT  CHECK (score >= 0 AND score <= 100),
    CONSTRAINT enrollment_pk PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(student_id),
    FOREIGN KEY (course_id)  REFERENCES course(course_id)
);

④ 여기가 핵심. student_id 하나로도, course_id 하나로도 행을 특정 못 한다 → 둘을 묶어 복합 PK(CONSTRAINT enrollment_pk PRIMARY KEY (student_id, course_id)). 같은 학생이 같은 강의를 두 번 등록하는 걸 막는다. FK 2개로 학생·강의 양쪽을 참조한다.

💡 enrollment가 바로 강의에서 말한 “N:M → 중간 테이블로 1:N 분해” 의 실물이다. 학생(N)과 강의(M)의 다대다를, 학생–enrollment와 강의–enrollment 두 개의 1:N으로 풀었다.

02 · 제약조건 시연 — NOT NULL / DEFAULT#

① 데이터를 넣으면서 제약이 어떻게 동작하는지 본다. 답지는 보통 “에러 나는 구문(주석)” + “정상 예시” 를 짝지어 보여준다.

-- ✅ 실제 답지 (예제01~02)
INSERT INTO department (dept_id, dept_name, location)
VALUES
    ('CSE',  '컴퓨터공학과', '공학관 3층'),
    ('ENG',  '영어영문학과', '인문관 2층'),
    ('MATH', '수학과',       '미정');      -- location 미입력 시 '미정' 자동

③ 출력: 3행 삽입 성공. MATH는 location을 안 줘도 DEFAULT '미정'이 채워진다.

④ 만약 dept_name을 빼고 INSERT하면? → NOT NULL 위반으로 에러. 즉 학과명 없는 학과는 못 만든다.

💡 NOT NULL = “이 칸은 비우고 못 지나간다”, DEFAULT = “비우면 내가 대신 채워준다”. 둘은 빈 값을 다루는 정반대 전략이다.

03 · 제약조건 시연 — UNIQUE (+ NULL은 중복 허용)#

① 중복 금지가 어떻게 걸리는지, 그리고 NULL은 왜 중복으로 안 치는지 확인한다.

-- ⚠ 에러 발생 구문 (예제03~04): 같은 email 중복 INSERT → UNIQUE 위반
-- INSERT INTO professor (...) VALUES ('P002', '김교수', '이미존재@univ.ac.kr', ...);

-- ✅ 실제 답지 (예제21): email이 NULL인 학생 2명 → 둘 다 성공
INSERT INTO student (student_id, name, email, birth_year, dept_id, grade)
VALUES
    ('S2001', '익명학생A', NULL, 2000, 'CSE', 1),
    ('S2002', '익명학생B', NULL, 2001, 'CSE', 2);

③ 출력: 같은 이메일 재삽입은 UNIQUE 위반 에러. 반면 이메일이 NULL인 두 학생은 둘 다 삽입 성공.

④ email엔 UNIQUE가 걸려 있지만, NULL은 “값이 없음"이라 비교 대상이 아니다 → NULL끼리는 중복으로 치지 않는다.

💡 강사 강조 그대로 — 이메일엔 UNIQUE ⭕, 이름엔 ❌(동명이인). 그리고 UNIQUE 컬럼이라도 NULL은 여러 개 가능하다는 게 이 예제의 핵심.

04 · 제약조건 시연 — CHECK#

① 값의 범위·조건을 벗어나면 막는다.

-- ⚠ 에러 발생 구문들 (예제06~07, 09)
-- credit = 5     → CHECK(credit BETWEEN 1 AND 3) 위반
-- hire_year=1950 → CHECK(hire_year >= 1980) 위반
-- grade = 5      → CHECK(grade BETWEEN 1 AND 4) 위반
INSERT INTO course (course_id, title, credit, prof_id)
VALUES ('C999', '학점오류강의', 5, 'P001');   -- credit 5 → 에러

③ 출력: CHECK 제약 위반 에러. 학점은 1~3만 허용되므로 5는 거부된다.

④ CHECK는 “이 범위 안에서만 들어와"라는 문지기다. 학점(13), 입사연도(≥1980), 학년(14), 점수(0~100) 등 비즈니스 규칙을 DB가 직접 강제한다.

05 · 제약조건 시연 — PK 중복 / FK 위반 / 복합 PK#

① 키 관련 위반 3종을 본다.

-- ⚠ 에러 발생 구문 (예제11): 존재하지 않는 학과 'GHOST' 참조 → FK 위반
INSERT INTO student (student_id, name, birth_year, dept_id, grade)
VALUES ('S9998', '유령학생', 2002, 'GHOST', 1);

③ 출력: FOREIGN KEY 위반 에러. department에 'GHOST'라는 dept_id가 없기 때문(참조 무결성).

④ 세 가지 위반 정리:

  • PK 중복(예제10): 이미 있는 student_id를 또 넣으면 → 개체 무결성 위반 에러.
  • FK 위반(예제11, 위 코드): 부모 테이블에 없는 값을 참조하면 → 참조 무결성 위반 에러. (단 00에서 PRAGMA foreign_keys = ON을 안 했으면 이 에러가 안 난다!)
  • 복합 PK 중복(예제12): 같은 (student_id, course_id) 쌍을 또 넣으면 → 에러. 한 학생이 같은 강의를 두 번 등록 못 함.

💡 부모 행을 DELETE할 때도 막힌다 — 자식(예: student)이 아직 그 학과를 참조 중이면 학과를 못 지운다. 그래서 강의 노트의 “DROP은 자식→부모 역순”.

06 · CONSTRAINT 명명 · PRAGMA로 제약 조회#

① 제약에 이름을 붙이면 관리가 쉽고, SQLite에선 제약을 PRAGMA로 조회한다.

-- ✅ 실제 답지 (예제13): 제약에 이름 부여
CREATE TABLE classroom (
    room_id   VARCHAR(10),
    building  VARCHAR(20) NOT NULL,
    capacity  INT,
    CONSTRAINT classroom_pk   PRIMARY KEY (room_id),
    CONSTRAINT capacity_check CHECK (capacity > 0 AND capacity <= 200)
);

-- ✅ 실제 답지 (예제20·27): SQLite의 제약 조회
PRAGMA table_info(student);          -- 컬럼·NOT NULL·PK 정보
PRAGMA foreign_key_list(enrollment); -- 외래키 목록

③ 출력: PRAGMA table_info(student)는 컬럼별 이름·타입·NOT NULL 여부·PK 여부를 표로 보여준다. foreign_key_list는 FK가 어느 테이블의 무엇을 참조하는지 보여준다.

④ CONSTRAINT 이름 제약(...) 형태로 이름을 주면, 나중에 조회·관리가 쉽다.

⚠️ SQLite 주의: 슬라이드의 SELECT * FROM information_schema.table_constraints;(MySQL)는 SQLite에 없다. SQLite에선 위처럼 PRAGMA를 쓴다.

07 · ⚠ SQLite ALTER 제약 우회#

① SQLite의 ALTER는 제한적이다. 가능한 것과 우회가 필요한 것을 구분한다.

-- ✅ 가능 (예제28): 컬럼 추가는 SQLite도 됨
ALTER TABLE student ADD COLUMN phone VARCHAR(20);

③ 출력: 컬럼 추가 성공.

④ 하지만 UNIQUE 추가 / DEFAULT 변경 / CHECK 삭제는 SQLite의 ALTER로 직접 못 한다(예제14~16). 우회 패턴은 이렇다.

-- ⚠ SQLite 우회 패턴 (새 테이블 → 복사 → 이름 바꾸기)
-- 1) 바뀐 제약으로 새 테이블 생성
CREATE TABLE student_new ( ... 원하는 제약 ... );
-- 2) 기존 데이터 복사
INSERT INTO student_new SELECT * FROM student;
-- 3) 기존 테이블 삭제 후 이름 변경
DROP TABLE student;
ALTER TABLE student_new RENAME TO student;

⚠️ 슬라이드의 ALTER TABLE ... MODIFY/CHANGE COLUMN, ADD/DROP CONSTRAINT는 MySQL 문법이다. SQLite 실습에선 위 재생성 패턴으로 처리한다는 점을 꼭 구분하자.

08 · 🔥 하이라이트 — constraint_demo (good.db vs bad.db)#

오늘의 백미. “UI는 똑같은데, 제약조건 설계가 틀리면 멀쩡한 사용자도 가입이 안 된다” 를 눈으로 보는 미니 프로젝트다. 같은 회원가입 화면(Streamlit)에 DB만 good.db(적절한 제약)와 bad.db(과도/잘못된 제약)를 바꿔 끼우고 결과를 비교한다.

실행법#

# constraint_demo 폴더에서
uv run streamlit run app.py

회원가입 INSERT — good/bad 동일!#

① 앱이 보내는 SQL은 양쪽이 완전히 같다. 차이는 오직 테이블을 어떻게 설계했는가에 있다.

-- ✅ 실제 답지 (good/bad 공통)
INSERT INTO users (username, email, password)
VALUES (?, ?, ?)

good.db — 적절한 제약 ✅#

-- ✅ 실제 답지 (good_db.py · init_db)
DROP TABLE IF EXISTS users;

CREATE TABLE users (
    user_id    INTEGER PRIMARY KEY AUTOINCREMENT,  -- PK: 자동 증가
    username   TEXT NOT NULL UNIQUE,                 -- NOT NULL + UNIQUE
    email      TEXT NOT NULL UNIQUE,                 -- NOT NULL + UNIQUE
    password   TEXT NOT NULL,                        -- NOT NULL (교육용 평문)
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    -- CHECK: 최소 길이·이메일 형식만 검증 (과도하지 않음)
    CHECK (length(username) >= 3),
    CHECK (length(password) >= 4),
    CHECK (email LIKE '%@%.%')
);

④ 제약이 최소한만 걸려 있다: PK(자동증가) + 필수·중복 금지 + “아이디 3자 이상 / 비번 4자 이상 / 이메일에 @와 . 있음”. 상식적인 입력이면 통과한다.

bad.db — 과도/잘못된 제약 ⚠#

-- ✅ 실제 답지 (bad_db.py · init_db)
DROP TABLE IF EXISTS users;
DROP TABLE IF EXISTS membership_plans;

-- FK 참조 대상 테이블 (plan_id의 부모)
CREATE TABLE membership_plans (
    plan_id   TEXT PRIMARY KEY,
    plan_name TEXT NOT NULL
);
-- 'BASIC'만 존재 — 'VIP'는 없음 (아래 DEFAULT와 불일치)
INSERT INTO membership_plans (plan_id, plan_name)
VALUES ('BASIC', '일반 회원');

CREATE TABLE users (
    user_id    INTEGER PRIMARY KEY AUTOINCREMENT,
    username   TEXT NOT NULL UNIQUE,
    email      TEXT NOT NULL UNIQUE,
    password   TEXT NOT NULL,
    -- 앱은 plan_id를 INSERT에 넣지 않음 → DEFAULT 'VIP' 적용
    plan_id    TEXT NOT NULL DEFAULT 'VIP',
    created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    -- 과도한 CHECK (강의 제약조건 비교용)
    CHECK (length(username) >= 10 AND length(username) <= 12),
    CHECK (username GLOB '[a-z0-9]*'),
    CHECK (email LIKE '%@school.ac.kr'),
    CHECK (length(password) = 8),
    CHECK (password GLOB '*[0-9]*' AND password GLOB '*[A-Z]*'),
    FOREIGN KEY (plan_id) REFERENCES membership_plans(plan_id)
);

④ 무엇이 잘못됐나:

  • 아이디 10~12자 + 소문자/숫자만 → 짧은 user1 같은 평범한 아이디 거부
  • 이메일 @school.ac.kr만 허용 → gmail·naver 거부
  • 비번 정확히 8자 + 숫자·대문자 필수 → 과도
  • 결정타: plan_id의 DEFAULT가 'VIP'인데 membership_plans엔 'BASIC'만 있다. 앱은 plan_id를 안 보내니 DEFAULT 'VIP'가 들어가고 → 존재하지 않는 값이라 FK 위반 → 어떤 입력을 해도 가입 자체가 실패한다.

구분good.dbbad.db
아이디3자 이상10~12자, 소문자·숫자만
이메일일반 형식(@,.)@school.ac.kr만 허용
비밀번호4자 이상정확히 8자, 숫자+대문자 필수

시나리오 흐름 (README 7개 중 학습 골자)#

#입력good.dbbad.db
1kim / kim@test.com / 1234✅ 가입 성공—
2위와 동일 입력—❌ CHECK 위반(아이디 길이·이메일 도메인·비번)
3bad의 CHECK를 전부 만족(kimminjun01 / minjun@school.ac.kr / Pass1234)—❌ FK 위반(plan_id ‘VIP’ 없음)
4good에서 같은 아이디·이메일 재가입❌ UNIQUE 위반—
5빈 값 제출앱 단 검증에서 차단(NOT NULL 도달 전)〃

💡 이 데모의 교훈: 시나리오 3이 핵심이다. CHECK를 다 통과해도 잘못된 FK+DEFAULT 설계 때문에 INSERT 자체가 불가능하다 — 앱은 plan_id를 안 보내는데, DB가 존재하지 않는 기본값을 강제하는 게 문제다. UI가 같아도 DB 설계(제약조건)에 따라 결과가 갈린다. 제약은 강력하지만, 잘못 설계하면 정상 사용자까지 막는 양날의 검이다. 그래서 강의의 한 문장 — 제약조건은 마지막 방어선이되, 비즈니스 로직에 근거해 설계해야 한다.

마무리#

오늘 실습은 school_db 5테이블을 제약조건·복합PK·FK까지 직접 CREATE하는 것에서 시작해, NOT NULL·UNIQUE(+NULL 중복 허용)·DEFAULT·CHECK·PK·FK가 위반 시 어떻게 막히는지를 예제로 확인했다. SQLite 특수성도 챙겼다 — FK는 PRAGMA foreign_keys = ON으로 켜야 하고, 제약 조회는 PRAGMA table_info/foreign_key_list, 제약 변경은 테이블 재생성으로 우회한다는 것. 그리고 하이라이트 constraint_demo에서, 동일한 UI·동일한 INSERT인데 제약 설계만으로 good.db는 가입되고 bad.db는 (과도한 CHECK + 잘못된 FK+DEFAULT 때문에) 가입 자체가 불가능해지는 걸 시나리오로 봤다. 한 줄 결론 — 제약은 데이터를 지키는 마지막 방어선이지만, 설계가 틀리면 정상 사용자까지 막는다.
