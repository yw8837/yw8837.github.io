🧪 실습 노트#

실습 DB는 chinook다. 주요 관계(키)는 다음과 같다(조인·서브쿼리에서 계속 쓰인다).

artists.ArtistId      ↔ albums.ArtistId
albums.AlbumId        ↔ tracks.AlbumId
genres.GenreId        ↔ tracks.GenreId
invoices.InvoiceId    ↔ invoice_items.InvoiceId
customers.CustomerId  ↔ invoices.CustomerId
employees.EmployeeId  ↔ customers.SupportRepId
invoice_items.TrackId ↔ tracks.TrackId

순서:

  1. 집계 함수 (COUNT · SUM · AVG · MAX · MIN) + LIMIT

  3. INNER JOIN 실습
  4. LEFT / RIGHT JOIN + NULL 필터링 실습

01 · 집계 함수 + LIMIT (슬라이드 예시)#

① 한 줄 설명 — 여러 행을 하나의 요약값으로 만드는 함수들. (슬라이드 예시 쿼리 — 가상 테이블 book/grade 기준)

② 코드 (출처: 슬라이드 「SQL과 함수」 예시)

-- COUNT: 개수 (NULL 제외)
SELECT COUNT(id) FROM book;   -- id 값의 개수
SELECT COUNT(*)  FROM book;   -- 전체 행 개수

-- SUM / AVG
SELECT SUM(math) FROM grade;
SELECT AVG(korean), AVG(english), AVG(math) FROM grade;

-- MAX / MIN
SELECT MAX(korean) FROM grade;
SELECT MIN(english) FROM grade;

-- LIMIT (인덱스 시작 0)
SELECT * FROM book LIMIT 5;     -- 앞 5개
SELECT * FROM book LIMIT 1, 5;  -- 2번째부터 5개

③ 출력 결과 — 각각 개수·합계·평균·최대·최소 값이 한 줄로, LIMIT는 지정 개수만큼 행이 나온다.

④ 한 줄씩 뜯어보기

  • COUNT(id) vs COUNT(*) : 전자는 id가 NULL인 행을 빼고, 후자는 전체 행을 센다.
  • AVG(korean), AVG(english), AVG(math) : 평균을 여러 개 동시에.
  • LIMIT 1, 5 : 시작 인덱스 1(= 두 번째)부터 5개.

⑤ 💡 팁 — 위 쿼리는 슬라이드의 가상 테이블(grade 등) 기준이라 chinook에선 그대로 안 돈다. chinook 적용은 다음 절(GROUP BY)에서 한다. LIMIT 시작, 개수 문법은 DBMS마다 달라(Oracle 상이) 주의.

02 · GROUP BY / HAVING 실습 (chinook)#

① 한 줄 설명 — 기준 컬럼으로 묶어 집계(GROUP BY)하고, 그 그룹에 조건을 건다(HAVING).

② 코드 (문제 출처: Day02_groupby_Join_student.sql)

GROUP BY 워밍업 15는 노션에 답지가 없어 재구성, HAVING 610은 노션 실제 답지 그대로다.

-- ⚠ 재구성 (문제 1~5: 노션 답지 없음, 슬라이드 문법 기반)
-- 문제 1. 아티스트별 앨범 수
SELECT ArtistId, COUNT(*) FROM albums GROUP BY ArtistId;
-- 문제 2. 앨범별 트랙 수
SELECT AlbumId, COUNT(*) FROM tracks GROUP BY AlbumId;
-- 문제 3. 국가별 매출 합계
SELECT BillingCountry, SUM(Total) FROM invoices GROUP BY BillingCountry;
-- 문제 4. 장르별 평균 재생시간
SELECT GenreId, AVG(Milliseconds) FROM tracks GROUP BY GenreId;
-- 문제 5. 국가별 고객 수 (많은 순)
SELECT Country, COUNT(*) FROM customers GROUP BY Country ORDER BY COUNT(*) DESC;

-- ✅ 실제 답지 (노션 260609, 문제 6~10) — HAVING으로 그룹에 조건

-- 문제 6. 앨범이 5개 이상인 아티스트만
SELECT ArtistId, COUNT(*) AS album_cnt
FROM albums GROUP BY ArtistId
HAVING COUNT(*) > 5;
-- 문제 7. 트랙이 15개를 초과하는 앨범만
SELECT AlbumId, COUNT(*) as track_cnt
FROM tracks GROUP BY AlbumId
HAVING COUNT(*) > 15;
-- 문제 8. 매출 합계가 100을 초과하는 국가만
SELECT BillingCountry, SUM(Total) as total_sales
FROM invoices GROUP BY BillingCountry
HAVING SUM(Total) > 100;
-- 문제 9. 인보이스가 7건 이상인 고객만
SELECT CustomerId, COUNT(*) as invoice_cnt
FROM invoices GROUP BY CustomerId
HAVING COUNT(*) >= 7;
-- 문제 10. 트랙이 100개 이상인 장르만, 많은 순
SELECT GenreId, COUNT(*) as track_cnt
FROM tracks GROUP BY GenreId
HAVING COUNT(*) >= 100
ORDER BY 2 DESC;

📎 답지 디테일: 문제 6은 문제 지문이 “5개 이상"이지만 강사 답지 SQL은 HAVING COUNT(*) > 5(=6개 이상)로 되어 있다. 지문과 1 차이가 나니 그대로 옮기되 참고만. 문제 10의 ORDER BY 2는 “SELECT의 2번째 컬럼(track_cnt)으로 정렬"이라는 뜻 — 컬럼명 대신 순번으로 정렬하는 문법이다.

③ 출력 결과 — 각 그룹의 기준 컬럼 + 집계값(개수·합계·평균)이 출력된다. HAVING이 붙은 6~10은 조건을 통과한 그룹만 남는다.

④ 한 줄씩 뜯어보기

  • GROUP BY ArtistId : ArtistId가 같은 행끼리 묶는다.
  • SELECT ArtistId, COUNT(*) : 기준 컬럼(ArtistId)을 SELECT에 함께 넣는 게 정석.
  • HAVING COUNT(*) >= 5 : 묶은 **결과(그룹)**에 조건. WHERE가 아니라 HAVING.
  • ORDER BY COUNT(*) DESC : 집계값 기준 정렬.

⑤ 💡 팁 — WHERE는 그룹화 전 행 필터, HAVING은 그룹화 후 그룹 필터. “개수가 N 이상” 같은 집계 조건은 무조건 HAVING이다.

03 · INNER JOIN 실습 (chinook)#

① 한 줄 설명 — 두(또는 그 이상) 테이블을 키로 연결해 교집합을 가져온다.

② 코드 (문제 출처: Day02_groupby_Join_student.sql)

1113은 재구성, **1416은 노션 실제 답지 그대로**다.

-- ⚠ 재구성 (문제 11~13: 노션 답지 없음)
-- 문제 11. 앨범 제목 + 아티스트명
SELECT albums.Title, artists.Name
FROM albums INNER JOIN artists ON albums.ArtistId = artists.ArtistId;
-- 문제 12. 트랙명 + 장르명 (컬럼명 Name 중복 → 별칭으로 구분)
SELECT tracks.Name AS TrackName, genres.Name AS GenreName
FROM tracks INNER JOIN genres ON tracks.GenreId = genres.GenreId;
-- 문제 13. 인보이스 + 고객명
SELECT invoices.InvoiceId, invoices.Total, customers.FirstName, customers.LastName
FROM invoices INNER JOIN customers ON invoices.CustomerId = customers.CustomerId;

-- ✅ 실제 답지 (노션 260609, 문제 14~16)

-- 문제 14. 인보이스 상세 + 트랙 (항목ID·트랙명·단가·수량)
SELECT invoice_items.InvoiceLineId,
       tracks.Name,
       invoice_items.UnitPrice,
       invoice_items.Quantity
FROM invoice_items
INNER JOIN tracks
  ON invoice_items.TrackId = tracks.TrackId;

-- 문제 15. 고객 + 담당 직원 (customers.SupportRepId = employees.EmployeeId)
SELECT customers.FirstName AS customer_name,
       employees.FirstName AS support_rep
FROM customers
INNER JOIN employees
  ON customers.SupportRepId = employees.EmployeeId;

-- 문제 16. 트랙-앨범-아티스트 3개 조인 (앨범 경유, 앞 20건)
SELECT tracks.Name AS track_name,
       albums.Title AS album_title,
       artists.Name AS artist_name
FROM tracks
INNER JOIN albums  ON tracks.AlbumId = albums.AlbumId
INNER JOIN artists ON albums.ArtistId = artists.ArtistId
LIMIT 20;

📎 문제 15가 바로 강의에서 강조한 데이터 정의서(Data Dictionary) 사례다 — customers.SupportRepId는 이름만 봐선 모르지만, 정의서를 보면 “담당 직원 employees.EmployeeId“임을 알 수 있어 이 조인이 가능하다.

③ 출력 결과 — 두 테이블의 컬럼이 한 행에 합쳐져 나온다. 매칭 안 되는 행은 빠진다(교집합).

④ 한 줄씩 뜯어보기

  • INNER JOIN artists ON albums.ArtistId = artists.ArtistId : 두 테이블을 잇는 키를 ON으로.
  • tracks.Name AS TrackName, genres.Name AS GenreName : 두 테이블에 같은 Name 컬럼이 있어 별칭으로 구분(안 하면 ambiguous 오류).
  • 문제 16 : 트랙↔아티스트는 직접 연결이 없어 앨범을 경유(2단 조인).

⑤ 💡 팁 — 조인이 잘 됐는지 SELECT *로 먼저 확인 후 컬럼을 좁히는 게 요령. 단 실무에선 SELECT * 지양. 컬럼명이 겹치면 항상 table.column 또는 별칭으로 명시하자.

04 · LEFT / RIGHT JOIN + NULL 필터링 (chinook)#

① 한 줄 설명 — 한쪽 테이블을 전부 보존하는 조인. NULL을 거르면 “관계 없는 행"을 찾을 수 있다.

② 코드 (문제 출처: Day02_groupby_Join_student.sql)

1718(NULL 필터링)은 재구성, **1920은 노션 실제 답지 그대로**다.

-- ⚠ 재구성 (문제 17~18: 노션 답지 없음 — NULL 필터링 핵심 패턴)
-- 문제 17. 모든 아티스트 기준 앨범 LEFT JOIN (앨범 없는 아티스트도 포함)
SELECT artists.Name, albums.Title
FROM artists LEFT JOIN albums ON artists.ArtistId = albums.ArtistId;
-- 문제 18. 앨범이 하나도 없는 아티스트만 (오른쪽이 NULL)
SELECT artists.Name
FROM artists LEFT JOIN albums ON artists.ArtistId = albums.ArtistId
WHERE albums.AlbumId IS NULL;

-- ✅ 실제 답지 (노션 260609, 문제 19~20)

-- 문제 19. 모든 앨범 기준으로 아티스트 연결 (RIGHT JOIN, SQLite 3.39.0+)
SELECT artists.Name, albums.Title
FROM artists
RIGHT JOIN albums
  ON artists.ArtistId = albums.ArtistId;

-- 문제 20. 19와 '같은 결과'를 RIGHT 없이 LEFT로 (구버전 호환: 테이블 순서 뒤집기)
SELECT artists.Name, albums.Title
FROM albums
LEFT JOIN artists
  ON artists.ArtistId = albums.ArtistId;

③ 출력 결과 — 17은 앨범 없는 아티스트가 Title이 NULL로, 18은 그 NULL 행만, 19·20은 모든 앨범 기준 결과가 같게 나온다.

④ 한 줄씩 뜯어보기

  • LEFT JOIN : 왼쪽(artists) 전부 + 매칭 실패 시 오른쪽은 NULL.
  • WHERE albums.AlbumId IS NULL : 매칭 실패(= 앨범 없음)한 행만. NULL은 반드시 IS NULL로 거른다(= NULL 안 됨).
  • 문제 20 : albums LEFT JOIN artists로 테이블 순서를 바꿔 RIGHT JOIN 효과를 LEFT로 재현.

⑤ 💡 팁 — RIGHT JOIN보다 LEFT JOIN을 권장(테이블 순서로 대체 가능). RIGHT JOIN은 SQLite 3.39.0 이상에서만 동작하니, 버전이 낮으면 문제 19가 에러 날 수 있다.

05 · 서브쿼리 실습 (chinook)#

① 한 줄 설명 — 쿼리 안에 또 다른 쿼리를 넣어 “모르는 기준"으로 검색한다. 단일행·다중행·스칼라·FROM·EXISTS 형태를 모두 다룬다.

② 코드 (문제 출처: Day02_subquery_student.sql)

노션에 답지가 있는 1·4·5·6·10은 실제 답지 그대로, 나머지는 강의에서 다룬 개념(ANY/ALL→MIN/MAX·스칼라·FROM·EXISTS)을 익히는 재구성 추가연습이다.

-- ✅ 실제 답지 (노션 260609)

-- 문제 1. [단일행 >] 'Balls to the Wall'(342562ms)보다 긴 트랙
SELECT Name, Milliseconds FROM tracks
WHERE Milliseconds > (
    SELECT Milliseconds FROM tracks WHERE Name = 'Balls to the Wall'
);

-- 문제 4. [단일행 =] 앨범 'Let There Be Rock' 수록 트랙
SELECT Name FROM tracks
WHERE AlbumId = (
    SELECT AlbumId FROM albums WHERE Title = 'Let There Be Rock'
);

-- 문제 5. [단일행 <] 전체 평균 Total보다 작은 인보이스
SELECT InvoiceId, Total FROM invoices
WHERE Total < (SELECT AVG(Total) FROM invoices);

-- 문제 6. [다중행 IN, 중첩] 'AC/DC'가 발매한 앨범의 모든 트랙
SELECT Name FROM tracks
WHERE AlbumID IN (
    SELECT AlbumId FROM albums
    WHERE ArtistId = (SELECT ArtistId FROM artists WHERE Name = 'AC/DC')
);

-- 문제 10. [다중행 IN] 'Rock' 장르 트랙이 하나라도 포함된 앨범 제목
SELECT Title FROM albums
WHERE AlbumId IN (
    SELECT AlbumId FROM tracks
    WHERE GenreId = (SELECT GenreId FROM genres WHERE Name = 'Rock')
);

-- ⚠ 재구성 추가연습 (노션 답지 없음 — 강의에서 다룬 개념 연습용)

-- [SQLite 보강 ALL→MAX] 'Rock' 모든 트랙보다 긴 트랙 (ANY/ALL 미지원 → MAX 대체)
SELECT Name FROM tracks
WHERE Milliseconds > (
    SELECT MAX(Milliseconds) FROM tracks
    WHERE GenreId = (SELECT GenreId FROM genres WHERE Name = 'Rock'));

-- [SQLite 보강 ANY→MIN] 'Jazz' 트랙 중 하나라도보다 긴 트랙 (ANY → MIN 대체)
SELECT Name FROM tracks
WHERE Milliseconds > (
    SELECT MIN(Milliseconds) FROM tracks
    WHERE GenreId = (SELECT GenreId FROM genres WHERE Name = 'Jazz'));

-- [스칼라(SELECT절)·상관 서브쿼리] 앨범별 트랙 수
SELECT a.Title, (SELECT COUNT(*) FROM tracks t WHERE t.AlbumId = a.AlbumId) AS track_count
FROM albums a;

-- [FROM절 파생 테이블, 별칭 필수] 앨범별 트랙 수의 전체 평균
SELECT AVG(cnt) FROM (
    SELECT AlbumId, COUNT(*) AS cnt FROM tracks GROUP BY AlbumId) AS sub;

-- [NOT EXISTS, NULL 안전] 한 번도 구매 안 된 트랙
SELECT Name FROM tracks t
WHERE NOT EXISTS (SELECT 1 FROM invoice_items ii WHERE ii.TrackId = t.TrackId);

③ 출력 결과 — 각 조건을 만족하는 트랙/앨범/인보이스가 출력된다. 스칼라 서브쿼리는 앨범마다 트랙 수가 옆 컬럼에, FROM 파생은 평균값 한 줄, NOT EXISTS는 한 번도 안 팔린 트랙 목록이 나온다.

④ 한 줄씩 뜯어보기

  • 문제 1·5 : 서브쿼리가 값 1개(특정 트랙 길이 / 전체 평균)를 돌려주는 단일행 서브쿼리 → >·< 비교.
  • 문제 4 : 앨범 1개의 AlbumId는 단일 값 → = 사용.
  • 문제 6 : 서브쿼리를 3단 중첩(artists→albums→tracks). 노션 답지에도 “분할 → 각각 실행 → 합치기” 단계가 그대로 적혀 있는 대표 문항.
  • 문제 10 : ‘Rock’ 장르의 GenreId → 그 장르 트랙의 AlbumId(다중) → 그 앨범 제목. 다중행이라 IN.
  • (재구성) ANY/ALL → SQLite엔 없어 MAX/MIN으로 대체(ALL→MAX, ANY→MIN). 스칼라는 JOIN과 같은 결과, FROM 파생은 별칭(AS sub) 필수, NOT EXISTS는 NULL에 안전.

⑤ 💡 팁 — 서브쿼리는 **“분할 → 각각 실행 → 합치기”**로 접근하자. 안쪽 서브쿼리만 따로 돌려 값이 맞는지 확인한 뒤 바깥 쿼리와 합치면 디버깅이 훨씬 쉽다. 특히 문제 6처럼 중첩이 깊을수록 안쪽부터 하나씩.

참고: NOT IN은 서브쿼리 결과에 NULL이 있으면 아무것도 반환 안 할 수 있어, “구매 안 된 트랙”(문제 9/19) 같은 건 NOT EXISTS가 안전하다(파일 주석에도 명시). 조인과 서브쿼리는 같은/유사 결과가 나오는 경우가 있어 “정답은 하나가 아니다”.

마무리#

오늘 실습은 SELECT 위에 네 층을 쌓았다 — 집계 함수(요약), GROUP BY/HAVING(그룹 집계·필터), JOIN(테이블 결합), 서브쿼리(쿼리 중첩). 양이 많지만 관통하는 한 가지는 **“분할 → 각각 실행 → 합치기”**다. 복잡한 쿼리는 한 번에 쓰려 하지 말고 조각으로 나눠 검증하자. 그리고 SQLite 특이점(ANY/ALL→MIN/MAX, RIGHT JOIN 버전 제약)과 NULL의 함정(IS NULL, NOT IN vs NOT EXISTS)을 꼭 기억하자. ✅ 실제 답지는 강사 노션 원본이니 그대로 믿고, ⚠ 재구성만 참고로 보며 자기 식으로 다시 풀어보는 게 진짜 실습이다.
