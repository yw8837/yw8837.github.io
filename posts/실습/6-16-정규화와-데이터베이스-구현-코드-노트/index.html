00 · 4단계 데모 구성 — 같은 데이터, 4개 DB#

① 이 데모의 아이디어는 한 줄이다 — 완전히 같은 학생·수강 데이터를 비정규화·1NF·2NF·3NF 네 단계 DB에 각각 저장해두고, 똑같은 갱신/삽입/삭제 작업을 해보며 어느 단계에서 사고(이상현상)가 나는지 비교한다.

② 공통 시드 데이터 (README 표 / norm_db.py 주석):

학번 학생 학과 수강
101 김민준 CS 컴퓨터공학 CS301(A+), CS302(A)
102 이서연 EE 전자공학 CS301(B+)
  • 과목: CS301 데이터베이스(김교수, 301호), CS302 운영체제(박교수, 302호)
  • 학과: CS 컴퓨터공학(공학관 A동), EE 전자공학(공학관 B동)

④ 같은 데이터를 4번 저장하는 이유는, “입력은 같은데 정규화 단계만 다르면 결과가 어떻게 갈리는지” 를 통제된 비교로 보기 위해서다. UI도 입력도 동일하고, 오직 테이블 설계만 다르다.

01 · 🔥 하이라이트 — normalization_compare (이상현상 4단계 비교)#

오늘의 백미. Streamlit 앱에서 4개 탭(비정규화/1NF/2NF/3NF)을 두고, 동일한 작업을 단계별로 실행해 이상현상을 눈으로 비교한다.

실행법#

cd normalization_compare
uv sync
uv run streamlit run app.py
# http://localhost:8501

★ 핵심 — 단계별 이상 상태 표#

① 이 표가 오늘 실습 전체의 결론이다 (README + norm_db.py의 SCENARIO_ANOMALY).

단계 갱신(학과) 갱신(교수) 삽입 삭제 종합
비정규화 존재 존재 존재 존재 ❌ 이상 구조
1NF 존재 존재 존재 존재 ❌ 이상 구조
2NF 잔존 정상 정상 정상 ⚠ 이행 종속 잔존
3NF 정상 정상 정상 정상 ✅ 정상

④ 표 읽는 법 — norm_db.py의 라벨 그대로:

  • risk=“이상 존재” → 비정규화·1NF: 구조적으로 이상에 취약
  • partial=“일부 잔존” → 2NF: 부분 종속은 해소됐지만 이행 종속 때문에 학과 갱신 이상만 남음
  • ok=“정상” → 3NF: 모든 이상 해소

💡 이 표의 핵심은 2NF 행이다. 2NF는 부분 종속을 없앴는데도 학과 갱신 한 칸만 “잔존” 이다. 바로 그 한 칸이 2NF와 3NF의 차이(이행 종속)를 눈으로 보여준다 — 학과를 독립 테이블로 빼는 3NF가 되어야 그 칸도 “정상"이 된다.

4가지 시나리오 (norm_db.py 함수 / README ➊~➍)#

① 같은 작업을 4단계 DB에서 각각 실행해, 단계마다 결과가 어떻게 다른지 본다.

➊ 학과 건물 변경 = 갱신 이상 (update_dept_building) — 학과코드 + 새 건물명 입력

  • 비정규화/1NF: 같은 학과 정보가 여러 행에 중복 → “첫 row만 수정하면 같은 학과인데 건물이 row마다 달라질 수 있음”
  • 2NF: student_2nf에 학과가 학생별로 중복 → “dept_building이 학생 row마다 다를 수 있음”(이행 종속 잔존)
  • 3NF: UPDATE department ... WHERE dept_code = ? → 학과 마스터 1곳만 수정(정상)

➋ 교수 연구실 변경 = 갱신 이상 (update_professor_office) — 과목코드 + 새 연구실 입력

  • 비정규화: 다중값 셀 전체를 다시 저장해야 함 / 1NF: 해당 과목의 모든 수강 row 수정 필요
  • 2NF: UPDATE course_2nf ... 1 row → 모든 수강 조회에 반영(정상) / 3NF: UPDATE professor ... 1 row(정상)

➌ 수강 등록 = 삽입 이상 (add_enrollment) — 학번/과목/성적 입력 (기본 과목명 ‘네트워크’, 교수 ‘최교수’, 연구실 ‘401호’)

  • 비정규화: 다중값 셀에 콤마로 이어 붙임 → 원자값·무결성 위반 / 1NF: 원자값 삽입은 되지만 학과·교수 정보가 row마다 중복
  • 2NF/3NF: enrollment/enrollment_3nf에 성적만 추가(과목 없으면 마스터 테이블에 먼저 INSERT) → 정상

➍ 학생 수강 삭제 = 삭제 이상 (delete_student_records) — 학번 입력

  • 비정규화: 학생 row 삭제 → 해당 학생·수강·학과 정보가 모두 사라짐 / 1NF: 수강 row 삭제 → 학생 마스터가 없어 학생 정보 복구 불가
  • 2NF/3NF: enrollment에서 수강만 삭제 → student_2nf/student 마스터에 학생 정보 유지(정상)

⑤ 추가로 check_data_issues가 각 단계의 실제 데이터 불일치를 자동 탐지한다 — 비정규화는 course_ids 중복, 1NF는 “같은 학생인데 dept_building이 row마다 다름”/“과목 교수 연구실이 row마다 다름”, 2NF는 “학과 dept_building이 학생 row마다 다름”, 3NF는 (정상이면) 없음.

💡 데모 전체의 학습 포인트: UI·입력이 같아도 DB 정규화 단계에 따라 이상현상 발생 여부가 달라진다. 비정규화·1NF는 구조적으로 이상에 취약, 2NF는 부분 종속만 해소돼 학과 갱신 이상이 잔존, 3NF에서 모든 이상이 해소된다.

02 · 정규화 SQL ① 비정규화 → 1NF (원자값) ✅#

① 위 데모가 내부에서 단계별로 쓰는 테이블 구조를, 답지 SQL로 직접 본다. 먼저 모든 게 한 테이블에 들어간 비정규화 상태다.

[0단계] 비정규화 — student_course_all (다중값, PK 없음)

-- ✅ 실제 답지 (비정규화.sql)
CREATE TABLE student_course_all (
    student_id       INTEGER,
    student_name     TEXT,
    course_ids       TEXT,
    course_names     TEXT,
    grades           TEXT,
    professor_name   TEXT,
    professor_office TEXT,
    dept_code        TEXT,
    dept_name        TEXT,
    dept_building    TEXT
);

④ 무엇이 문제인가:

  • PK가 없다 → 행을 유일하게 식별 못 함
  • course_ids·course_names·grades가 다중값(콤마 구분) → WHERE·JOIN·ORDER BY가 정상 동작 불가
  • 학생이 N과목 수강하면 professor_name·dept_name 등이 행마다 중복 복제

⚠ 메모(원문 차이 보존): norm_db.py 안의 동명 테이블은 student_id INTEGER PRIMARY KEY + professor_names/professor_offices(복수형)로 정의돼 있다(다중값 강조 + 4단계 공존을 위한 변형). 답지 비정규화.sql(위)은 professor_name/professor_office(단수형)다. 둘 다 원문 그대로 인용한다.

[1NF] 원자값 + 복합 PK — student_course_1nf

-- ✅ 실제 답지 (1NF.sql)
CREATE TABLE student_course_1nf (
    student_id       INTEGER,
    course_id        TEXT,
    student_name     TEXT,
    course_name      TEXT,
    grade            TEXT,
    professor_name   TEXT,
    professor_office TEXT,
    dept_code        TEXT,
    dept_name        TEXT,
    dept_building    TEXT,
    PRIMARY KEY (student_id, course_id)
);

④ 무엇이 바뀌었나(= 1NF가 제거한 것): 다중값 컬럼(course_ids 등)을 원자값으로 풀고, 한 행 = “한 학생의 한 과목"이 되도록 복합 PK (student_id, course_id) 를 줬다. 아직 남은 문제: 여전히 단일 테이블이라 student_name·학과·교수 정보가 행마다 중복된다 → 2NF·3NF로.

03 · 정규화 SQL ② 2NF (부분 함수 종속 제거) ✅#

① 복합키 (student_id, course_id)의 일부에만 매달린 컬럼을 별도 테이블로 빼낸다. 1테이블 → 3테이블.

-- ✅ 실제 답지 (2NF.sql)
CREATE TABLE student_2nf (
    student_id    INTEGER PRIMARY KEY,
    student_name  TEXT NOT NULL,
    dept_code     TEXT,
    dept_name     TEXT,
    dept_building TEXT
);

CREATE TABLE course_2nf (
    course_id        TEXT PRIMARY KEY,
    course_name      TEXT NOT NULL,
    professor_name   TEXT,
    professor_office TEXT
);

CREATE TABLE enrollment (
    student_id INTEGER NOT NULL,
    course_id  TEXT    NOT NULL,
    grade      TEXT,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student_2nf(student_id),
    FOREIGN KEY (course_id)  REFERENCES course_2nf(course_id)
);

④ 무엇이 바뀌었나(= 2NF가 제거한 것):

  • student_name은 student_id에만 종속(부분 종속) → student_2nf로 분리
  • course_name·professor_*는 course_id에만 종속(부분 종속) → course_2nf로 분리
  • grade(성적)만 복합키 둘 다 필요(완전 종속) → 연결 테이블 enrollment에 남음

⚠ 메모(이행 종속 잔존): student_2nf 안에 dept_code/dept_name/dept_building 3컬럼이 아직 함께 있다. 학번 → 학과코드 → 학과건물이라는 이행 종속이 남아서, 데모에서 “2NF 학과 갱신 이상 잔존(partial)“으로 나타난다. → 3NF에서 해소.

04 · 정규화 SQL ③ 3NF (이행 함수 종속 제거) ✅#

① 2NF에 남은 학번 → 학과코드 → 학과건물 이행 종속을 끊는다. 학과·교수를 독립 마스터 테이블로 분리하고 FK로 연결 → 5테이블.

-- ✅ 실제 답지 (3NF.sql)
CREATE TABLE department (
    dept_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    dept_code     TEXT UNIQUE NOT NULL,
    dept_name     TEXT NOT NULL,
    dept_building TEXT NOT NULL
);

CREATE TABLE professor (
    professor_id     INTEGER PRIMARY KEY AUTOINCREMENT,
    professor_name   TEXT NOT NULL,
    professor_office TEXT,
    dept_id          INTEGER,
    FOREIGN KEY (dept_id) REFERENCES department(dept_id)
);

CREATE TABLE student (
    student_id   INTEGER PRIMARY KEY,
    student_name TEXT NOT NULL,
    dept_id      INTEGER NOT NULL,
    FOREIGN KEY (dept_id) REFERENCES department(dept_id)
);

CREATE TABLE course (
    course_id    TEXT PRIMARY KEY,
    course_name  TEXT NOT NULL,
    professor_id INTEGER NOT NULL,
    FOREIGN KEY (professor_id) REFERENCES professor(professor_id)
);

CREATE TABLE enrollment_3nf (
    student_id INTEGER NOT NULL,
    course_id  TEXT    NOT NULL,
    grade      TEXT,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(student_id),
    FOREIGN KEY (course_id)  REFERENCES course(course_id)
);

④ 무엇이 바뀌었나(= 3NF가 제거한 것):

  • 학과를 department 마스터로 분리 → student는 dept_id(FK)만 가짐 → 학번→학과코드→학과건물 이행 종속 해소(학과 건물은 이제 department 한 곳에서만 관리)
  • 교수를 professor 마스터로 분리 → course는 professor_id(FK)만 가짐
  • 결과: 모든 갱신/삽입/삭제 이상 해소(데모 3NF = 정상)

⚠ 메모(원문 차이 보존):

  • 연결 테이블 이름이 2NF는 enrollment, 3NF는 enrollment_3nf로 다르다 — norm_db.py가 4단계를 한 DB에 공존시키려 일부러 분리한 것이라 답지 원문 그대로 둔다.
  • norm_db.py의 3NF professor.dept_id는 INTEGER NOT NULL인데, 답지 3NF.sql(위)은 INTEGER(NOT NULL 없음)다. 분해 구조·FK는 동일하고, 원문 차이만 보존한다.

05 · ⚠ MySQL 기준 — DB 생성 / DCL / 인덱스 (SQLite와 차이)#

① 슬라이드 후반 DB 구현은 MySQL CLI 기준이다. 위 정규화 실습(SQLite)과 무엇이 다른지를 표로 정리한다. (개념 설명은 강의 노트 08~11 참고.)

② MySQL 기준 명령:

-- ⚠ MySQL 기준 — 데이터베이스 단위 관리
CREATE DATABASE shared_kickboard;
SHOW DATABASES;
USE shared_kickboard;
DROP DATABASE shared_kickboard;

-- ⚠ MySQL 기준 — DCL (사용자 권한 관리)
CREATE USER 유저이름@localhost IDENTIFIED BY '비밀번호';
GRANT ALL PRIVILEGES ON 데이터베이스.테이블 TO 유저이름@localhost;
FLUSH PRIVILEGES;
SHOW GRANTS FOR 유저이름@localhost;
REVOKE ALL ON 데이터베이스.테이블 FROM 유저이름@localhost;

-- ⚠ MySQL 기준 — 인덱스
CREATE INDEX 인덱스명 ON 테이블명(컬럼명);
SHOW INDEX FROM 테이블명;
ALTER TABLE 테이블명 DROP INDEX 인덱스명;

④ SQLite vs MySQL 차이 — 이 회차 핵심 주의점:

기능 MySQL (슬라이드) SQLite (실습)
DB 단위 CREATE DATABASE / USE 없음 (파일 1개 = DB 1개)
사용자·권한 CREATE USER·GRANT·REVOKE·SHOW GRANTS·FLUSH PRIVILEGES 없음 (사용자/권한 개념 자체가 없음)
인덱스 조회 SHOW INDEX FROM 테이블 미지원 → PRAGMA index_list(테이블)
인덱스 삭제 ALTER TABLE ... DROP INDEX 인덱스명 DROP INDEX 인덱스명; (문법 다름)
인덱스 생성 CREATE INDEX ... 동일
트랜잭션 COMMIT/ROLLBACK 동일(지원)
ENUM 자료형(킥보드 ERD) ENUM('대여','반납') 없음 → CHECK로 대체

⚠️ 정리: 실습 코드(정규화 SQL·norm_db.py)는 SQLite — INTEGER PRIMARY KEY AUTOINCREMENT·TEXT·PRAGMA foreign_keys = ON. 반면 DB 구현 슬라이드(위 명령들)는 MySQL 전용 기능을 다수 포함한다. 같은 SQL이라도 DBMS가 다르면 안 되는 게 있다는 걸 회차 내내 라벨로 구분했다.

  • 정규화 데모: normalization_compare/ — README.md(이상 상태 표 + 4시나리오), norm_db.py(sqlite3, SCENARIO_ANOMALY·check_data_issues·4개 작업 함수), app.py(Streamlit). 실행: cd normalization_compare && uv sync && uv run streamlit run app.py

📌 정리: 오늘 SQL은 거의 전부 ✅ 실제 답지(비정규화.sql/1NF.sql/2NF.sql/3NF.sql, norm_db.py)이고 변형하지 않았다. ⚠ 라벨은 MySQL 기준 슬라이드이거나 SQLite와의 차이를 가리킨다. 실습은 SQLite, DB 구현 슬라이드는 MySQL이라는 점을 코드마다 라벨로 구분했다.

마무리#

오늘 실습의 백미는 normalization_compare 다 — 완전히 같은 학생·수강 데이터를 비정규화·1NF·2NF·3NF 네 DB에 넣고, 같은 갱신/삽입/삭제를 해보며 어느 단계에서 이상현상이 나는지를 표 하나로 정리했다. 핵심은 2NF 행 — 부분 종속은 해소됐지만 학과 갱신 이상만 “잔존” 하고, 그 한 칸이 3NF(학과를 department로 분리)에서야 “정상"이 된다. 그 뒤 답지 SQL로 student_course_all → student_course_1nf → student_2nf/course_2nf/enrollment → department/professor/student/course/enrollment_3nf의 단계별 분해를 verbatim으로 따라가며, 각 단계가 어떤 종속(다중값·부분·이행)을 제거하는지 짚었다. 마지막으로 DB 구현 슬라이드의 MySQL 명령(DATABASE·DCL·인덱스)이 SQLite에선 안 되거나 문법이 다르다는 차이를 표로 구분했다. 한 줄 결론 — 입력이 같아도 정규화 단계가 낮으면 데이터가 꼬이고, 3NF에서 비로소 모든 이상이 사라진다.
